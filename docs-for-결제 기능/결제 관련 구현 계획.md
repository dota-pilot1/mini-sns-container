## 1. 범위 요약

**Phase 1 — 수동 결제 (지금 구현)**
- 관리자가 매달 입금 확인 후 "이번 달 입금 확인" 버튼으로 레코드 생성
- 계약별 납부 내역, 월별 미납자 리스트, 과거 이력 조회
- 환불 처리 (원본 보존, soft delete 방식)

**Phase 2 — 자동화 (추후, 본 문서 범위 밖)**
- 토스페이 심사 통과 후 webhook 핸들러 추가
- 계좌 연동, 카카오페이 등 확장
- 이때 별도 `channel: MANUAL | TOSS | KAKAO` 필드를 추가

## 2. 도메인 모델

### 2.1 애그리거트: `Payment`

```
Payment {
  id              UUID
  contractId      UUID             ← 어떤 계약에 대한 결제
  periodYearMonth String           ← "2026-04" 형식
  amount          Long             ← 입금액(원)
  paidAt          Instant          ← 실제 입금 확인 시각
  method          Method           ← CARD | CASH | BANK_TRANSFER
  status          Status           ← PAID | REFUNDED
  refundedAt      Instant?         ← 환불 처리 시각 (nullable)
  note            String?          ← 관리자 메모
  createdAt       Instant
}

Method: CARD(신용카드) | CASH(현금) | BANK_TRANSFER(인터넷뱅킹/계좌이체)
Status: PAID(정상 입금) | REFUNDED(환불 완료)
```

### 2.2 불변식

- `contractId` 는 존재하는 계약을 참조
- `(contractId, periodYearMonth, status=PAID)` 는 1건만 존재 → **유니크 제약**
  - `REFUNDED` 레코드는 중복 허용 (환불 이력 보존)
- `amount >= 0`
- `periodYearMonth` 는 계약의 `startDate ~ endDate` 범위 안
- `status=REFUNDED` 일 때 `refundedAt` 은 non-null

### 2.3 "미납(overdue)" 판정

- Payment 레코드 자체는 저장하지 않음 (파생 정보)
- 쿼리: **ACTIVE 계약 × 해당 월** 중 `status=PAID` 레코드 없는 건
- 정책: 기준월 = 오늘 날짜의 해당 월 (납기일 개념은 Phase 1 에선 단순화)

### 2.4 환불 처리 정책

- **환불 ≠ 삭제**. 원본 레코드를 `status=REFUNDED` 로 표시, `refundedAt` 기록
- UI 에서는 취소선 + "환불됨" 배지로 표시
- 회계/감사 관점에서 이력 보존
- **DELETE 는 "실수로 잘못 입력한 레코드"에만 사용** — 환불과 구분

## 3. 서버 API

### 3.1 엔드포인트

| Method | Path | 설명 |
|---|---|---|
| `POST` | `/api/payments` | 수동 입금 확인 등록 |
| `GET` | `/api/payments` | 필터 조회 (contractId, period, status) |
| `GET` | `/api/payments/overdue?period=2026-04` | 미납자 리스트 |
| `POST` | `/api/payments/{id}/refund` | 환불 처리 (status=REFUNDED) |
| `DELETE` | `/api/payments/{id}` | 실수 입력 완전 삭제 |

### 3.2 요청/응답 예시

**POST /api/payments**
```json
// 요청
{
  "contractId": "uuid",
  "periodYearMonth": "2026-04",
  "amount": 450000,
  "paidAt": "2026-04-15T10:30:00Z",
  "method": "BANK_TRANSFER",
  "note": "계좌이체 확인"
}

// 응답 201
{
  "id": "uuid",
  "status": "PAID",
  "refundedAt": null,
  ...위 필드 전부,
  "createdAt": "..."
}
```

**POST /api/payments/{id}/refund**
```json
// 요청
{ "note": "4월 10일 중도 퇴실로 인한 환불" }

// 응답 200
{ ...전체 필드, "status": "REFUNDED", "refundedAt": "..." }
```

**GET /api/payments/overdue?period=2026-04**
```json
[
  {
    "contractId": "uuid",
    "tenantName": "홍길동",
    "roomNumber": "702",
    "expectedAmount": 410000,   // 계약 월세
    "daysOverdue": 15
  }
]
```

## 4. 프론트 UX

### 4.1 네비게이션 변경

**현재**: `대시보드 / 방관리 / 입주자 / 관리자`
**결제 추가 후**: `대시보드 / 방관리 / 입주자 / **결제** / 관리자`

### 4.2 페이지 구성

**`/payments` — 결제 관리 메인**
- 상단: 기준월 선택기 (기본값 = 이번 달)
- 탭/섹션:
  1. **미납** — `useOverduePaymentsQuery(period)` → 계약별 카드 + "입금 확인" 버튼
  2. **완납** — 이번 달 `PAID` 리스트
  3. **환불** — `REFUNDED` 건 별도 섹션 또는 탭 (이력 조회용)
  4. **전체 이력** — 기간 필터로 과거 조회

**각 계약 행의 "입금 확인" 버튼 클릭** → `RegisterPaymentDialog`
  - 필드: 금액 (기본값=계약 월세), 입금일 (기본=오늘), 수단 (CARD/CASH/BANK_TRANSFER), 메모
  - 제출 → `POST /api/payments`

**PAID 레코드 우측 메뉴**
  - "환불 처리" → `RefundDialog` (사유 메모 입력) → `POST /api/payments/{id}/refund`
  - "삭제" → 실수 입력 복구용, confirm dialog 강제

### 4.3 기존 화면 통합 (읽기 전용)

**방 상세 페이지 — 현재 입주자 카드**
- "최근 입금 내역" 섹션 추가 (최신 3건)
- REFUNDED 건은 취소선 표시

**입주자 드로어**
- 동일한 "최근 입금 내역" 섹션

### 4.4 Phase 1 에서 **안 만드는** 것

- 자동 납기 알림 (카카오톡/문자)
- 부분납 UI (분납은 관리자가 금액 수정 + 메모로 표현)
- 연체료 계산
- 영수증 발급

## 5. 구현 순서 (커밋 단위)

### Phase 1.1 — 서버 (4 커밋)
1. `Payment` 도메인 + JPA 매핑 + Flyway 마이그레이션 (`V___create_payments.sql`)

## 6. 결정된 항목 (확정)

- [x] **status 는 PAID | REFUNDED 만**. PENDING 없음 (자동화 도입 시 재검토)
- [x] **method: CARD | CASH | BANK_TRANSFER** (신용카드/현금/인터넷뱅킹)
- [x] **채널(MANUAL/TOSS/...) 은 Phase 1에서 모델링 안 함** — Phase 2에 별도 `channel` 필드로 추가
- [x] **부분납**: Phase 1 에선 "1계약×1달=1 PAID 레코드" 원칙. 부분납은 금액 수정 + 메모로 표현
- [x] **자동 생성 X**: 관리자 확인 시에만 레코드 생성. 미납은 "레코드 없음"으로 파생
- [x] **환불은 soft delete**: `status=REFUNDED` + `refundedAt` 기록. 원본 보존
- [x] **DELETE 는 실수 입력용**: 환불과 구분. UI에서 confirm 강제
- [x] **결제 관리 메뉴 추가**: 헤더 nav에 `/payments` 진입점
- [x] **권한**: 로그인한 사용자 모두 결제 등록 가능. Role 분리(v6 4순위) 까지는 이대로
