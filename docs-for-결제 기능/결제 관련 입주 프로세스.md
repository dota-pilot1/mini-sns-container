# 결제 기반 입주 프로세스

2026-04-19 작성. Contract + Payment 상호작용 흐름 정리.
구현 계획 본문은 [결제 관련 구현 계획.md](결제%20관련%20구현%20계획.md) 참고.

---

## 1. 핵심 원칙

> **계약은 등록만으로 유효해지지 않는다. 보증금 또는 첫 달 월세 결제가 확인되어야 ACTIVE 상태가 된다.**

이게 현실 고시원 운영 흐름과 일치하고, "방은 잡았지만 돈은 안 낸" 애매한 상태를 시스템이 명시적으로 표현할 수 있게 해준다.

---

## 2. 계약 상태 다이어그램

```
       ┌─────────────────────────────────────────┐
       │                                         │
       │                                         │
       │   (관리자 "입주 처리" → 계약 등록)        │
       │                 │                       │
       │                 ▼                       │
       │          ┌─────────────┐                │
       │          │   PENDING   │                │
       │          │  (방 홀드)   │                │
       │          └──────┬──────┘                │
       │                 │                       │
       │  (보증금/첫 달 결제 확인)                 │
       │    또는 (예약 부도 → 삭제)                │
       │                 │                       │
       │     ┌───────────┴──────────┐            │
       │     ▼                      ▼            │
       │  ┌──────┐             ┌────────┐        │
       │  │ACTIVE│             │(삭제됨) │       │
       │  └───┬──┘             └────────┘        │
       │      │                                  │
       │      │                                  │
       │      │ (만기 도달) ──────┐               │
       │      │                   ▼               │
       │      │             ┌─────────┐          │
       │      │             │ EXPIRED │          │
       │      │             └─────────┘          │
       │      │                                  │
       │      │ (중도 해지) ──────┐              │
       │      │                   ▼               │
       │      │           ┌─────────────┐        │
       │      │           │ TERMINATED  │        │
       │      │           └─────────────┘        │
       │                                         │
       └─────────────────────────────────────────┘
```

**상태 4개**:
- `PENDING`: 계약 등록됨, 첫 결제 대기 중. 방은 홀드.
- `ACTIVE`: 첫 결제 확인됨. 계약 유효, 거주 중.
- `TERMINATED`: 중도 해지.
- `EXPIRED`: 만기 도달.

## 3. 전형적인 입주 시나리오 (Sequence)

```
관리자             시스템            입주자
  │                 │                 │
  │ ①입주 처리      │                 │
  │ (회원→계약 생성) │                 │
  ├────────────────►│                 │
  │                 │ Contract(PENDING)│
  │                 │ Room.status = 예약│
  │                 │                 │
  │                 │         ②이체   │
  │                 │◄────────────────┤
  │                 │  (보증금+첫 달)  │
  │                 │                 │
  │ ③입금 확인      │                 │
  ├────────────────►│                 │
  │                 │ Payment 생성     │
  │                 │ Contract→ACTIVE │
  │                 │ Room.status=입실 │
  │                 │                 │
  │                 │                 │
  │  ━━ 이후 매달 반복 ━━              │
  │                 │                 │
  │                 │         매달 이체│
  │                 │◄────────────────┤
  │ 입금 확인       │                 │
  ├────────────────►│ Payment 생성    │
  │                 │ (Contract 상태 유지)│
```

## 4. 상태별 실무 의미

### 4.1 `PENDING` (방 홀드 상태)
- **의미**: 입주자가 구두로 약속하거나 계약서는 썼지만 돈은 아직 안 냄
- **방 상태**: `예약`
  - 다른 입주자에게 배정 불가
  - 빈 방 카운트에서 빠짐
- **미납 리스트에 표시**: 가능 (보통 "보증금 미납" 같은 라벨)
- **관리자 액션**:
  - 입금 확인 → ACTIVE 전환
  - 예약 부도 판단 → 계약 삭제 + 방 해제

### 4.2 `ACTIVE` (정상 거주)
- **의미**: 보증금/첫 달 결제가 확인되어 계약 유효. 거주 중.
- **방 상태**: `입실`
- **매달 결제가 생성되어도 Contract 상태는 ACTIVE 유지**
  - Payment가 없는 달 = "이번 달 미납" 으로 별도 쿼리 (Contract 상태 안 건드림)
- **관리자 액션**:
  - 매달 입금 확인 → Payment 생성
  - 중도 해지 → TERMINATED 전환
  - 만기 도달 → EXPIRED 전환 (자동 or 수동)

### 4.3 `TERMINATED` (중도 해지)
- **의미**: 계약 기간 끝나기 전에 합의/일방적으로 종료
- **방 상태**: `공실` 또는 `청소`
- **과거 Payment 이력은 그대로 보존**
- 환불이 필요하면 → 해당 Payment 에 refund 처리

### 4.4 `EXPIRED` (만기 종료)
- **의미**: `endDate` 도달. 재계약 없음.
- **방 상태**: `공실` 또는 `청소`

---

## 5. ACTIVE 전환 트리거 상세

### 5.1 "첫 결제"의 정의

첫 Payment 레코드가 생성되는 순간 = ACTIVE 전환 순간.

**Phase 1 단순 규칙**: Payment 생성 시점에 Contract가 PENDING 이면 자동 ACTIVE 전환.
- 보증금과 첫 달 월세를 구분해서 체크하지 않음 (복잡도 ↑)
- 관리자가 판단해서 "이 정도면 확인 ok" 할 때 1건 등록하면 됨
- 예: 보증금 + 첫 달 합쳐서 이체받은 경우 Payment 1건으로 끝낼 수 있음

### 5.2 도메인 이벤트 흐름

```
RegisterManualPaymentUseCase
  │
  ├── Payment 생성
  │
  ├── Contract 조회
  │
  └── if Contract.status == PENDING:
          Contract.activate() → status = ACTIVE
          Room.status 동기화 (예약 → 입실)
```

### 5.3 엣지 케이스

- **이미 ACTIVE인 계약에 결제 추가**: status 변화 없음 (매달 결제)
- **TERMINATED/EXPIRED 계약에 결제 추가**: 원칙적으로 거부 (보증금 환급은 refund 사용)
- **PENDING 계약 환불**: 거의 불가능한 케이스 (Payment 자체가 없으므로). 계약 삭제로 처리.

---

## 6. 방 상태 동기화 정책

Contract 상태 ↔ Room 상태 매핑:

| Contract 상태 | Room 상태 | 비고 |
|---|---|---|
| (없음) | 공실 | 비어있음 |
| PENDING | 예약 | 홀드 중, 다른 배정 불가 |
| ACTIVE | 입실 | 거주 중 |
| TERMINATED | 공실 또는 청소 | 관리자 재량 |
| EXPIRED | 공실 또는 청소 | 관리자 재량 |

Room.status 는 이미 존재하는 enum 재활용. 새 상태 추가 불필요.

## 7. 이 모델의 자연스러운 확장 포인트

Phase 1 에서는 단순하게 유지하되, 나중에 다음이 필요하면 덧붙일 수 있음:

- **예약 자동 취소**: "PENDING 상태가 7일 지나면 자동 CANCEL" 크론 또는 정책
- **보증금/월세 분리 추적**:
  - 현재: Payment 1건으로 합쳐서 등록 가능
  - 확장: Payment 에 `type: DEPOSIT | RENT` 필드 추가 → 더 세밀한 상태 표현 가능
- **중간 상태 세분화**:
  - 예: `PARTIALLY_PAID` ("보증금은 받았는데 첫 달 월세 아직")
  - 지금은 필요 없음. 관리자가 "일부 입금" 메모로 처리
- **만기 자동 전환**: `endDate` 지난 ACTIVE 계약을 EXPIRED 로 자동 전환하는 일일 배치

## 8. 구현 결정이 필요한 항목

- [ ] **PENDING 추가를 Phase 1에 통합할지, Phase 1.5 로 분리할지**
  - 통합: 커밋 수 +2, 한 번에 완결. 리스크 ↑
  - 분리: Payment 먼저 안정화 후 Contract 상태 보강. 권장
- [ ] **PENDING 계약의 방 상태 자동 전환 범위**
  - 계약 생성 시 `공실 → 예약` 자동 전환할지
  - ACTIVE 전환 시 `예약 → 입실` 자동 전환할지
  - → 둘 다 자동 권장. 관리자 실수 방지.
- [ ] **기존 ACTIVE 계약 마이그레이션**
  - 현재 모든 Contract가 ACTIVE 로 생성됨
  - PENDING 도입 후 기존 데이터는 어떻게? → 모두 ACTIVE 유지 (재할당 안 함)
- [ ] **UI 표시 방식**
  - PENDING 계약 카드에 뭔가 눈에 띄는 표시 필요 ("보증금 미납 경고" 등)
  - 기본은 오렌지/노란 배지 정도
