# Step 5 — 프론트: 방 목록 + 등록/수정 UI

> 목표: Step 4에서 깐 API/라우트 뼈대 위에 **실제 관리자가 쓸 수 있는 화면**을 얹는다.
> MVP는 기능 완성도 > 디자인 완성도. Tailwind + 기존 `shared/ui` 재사용.

---

## 1. 페이지별 설계

### 1-1. `/rooms` — 방 목록 페이지 (3-뷰 토글)

**레이아웃**:

```
[상단 바]  방 관리                                    [ + 방 등록 ]
[뷰 전환]  ◉ 층별 카드   ○ 칸반(상태)   ○ 테이블
[필터 바]  [층 ▼] [상태 ▼] [타입 ▼]  [검색]
[뷰 영역]  ← 선택된 뷰에 따라 렌더링
```

#### 뷰 3종 — 각자 다른 업무를 커버

| 뷰            | 언제 쓰나                                  | 우선순위        |
| ------------- | ------------------------------------------ | --------------- |
| **층별 카드** | 공간 인지 — "2층 어디가 비었지?"           | **MVP (기본값)** |
| **칸반**      | 운영 워크플로우 — 청소중 → 공실 드래그     | Fast-follow     |
| **테이블**    | 숫자 비교/정렬 — 월세, 계약 만료일         | 계약 도메인 이후 |

> **MVP 범위**: 층별 카드만 완성도 있게. 나머지 2개는 뷰 전환 UI만 자리 잡아두고 "준비 중" placeholder.
> 같은 `useRoomsQuery` 데이터 위에 **뷰 컴포넌트만 갈아끼우는 구조**라 증분 비용이 작음.

#### 뷰 1 — 층별 카드 (메인)

```
[ 3층 ]
  ┌──────┐ ┌──────┐ ┌──────┐
  │ 301  │ │ 302  │ │ 303  │
  │ 공실 │ │ 입실 │ │ 청소 │
  └──────┘ └──────┘ └──────┘
[ 2층 ]
  ┌──────┐ ┌──────┐ ...
```

- 층 내림차순(또는 오름차순) 섹션으로 그룹핑.
- 카드 하나 = `RoomCard` (호수, 상태 배지, 월세 요약, 클릭 시 상세).
- 한 층에 방이 많으면 가로 스크롤 또는 래핑.

#### 뷰 2 — 칸반 (상태 집중) — placeholder로 시작

- 컬럼: VACANT / RESERVED / OCCUPIED / CLEANING / MAINTENANCE.
- 각 컬럼에 `RoomCard` 세로 나열.
- **Fast-follow 단계에서 드래그&드롭으로 `changeRoomStatus` 호출**. MVP에선 "준비 중" 표시.

#### 뷰 3 — 테이블 (계약 관리용) — 계약 도메인 생긴 이후

- `호수 | 층 | 평수 | 타입 | 월세 | 보증금 | 상태 | (계약 만료일) | 액션`.
- 계약 도메인이 붙기 전까진 계약 관련 컬럼은 비워둠. MVP에선 "계약 도메인 구현 후 활성화" 표시.

#### 공통 동작

- **뷰 상태 URL 동기화**: `/rooms?view=floor|kanban|table` — 새로고침/공유 시 유지.
- **필터 상태도 URL**: `/rooms?view=floor&floor=2&status=VACANT`.
- 상태 배지 색상: VACANT(초록), RESERVED(노랑), OCCUPIED(파랑), CLEANING(회색), MAINTENANCE(빨강).
- 빈 상태: "등록된 방이 없습니다" + 등록 버튼.
- 로딩: 스켈레톤 또는 기존 공용 스피너.
- 에러: 기존 에러 바운더리/토스트 사용.

**데이터**: `useRoomsQuery(filters)` — 뷰 3종이 **동일한 훅**을 공유. 뷰 전환 시 추가 API 호출 없음.

### 1-2. `/rooms/new` — 방 등록 페이지

**폼 필드** (step1 테이블과 동일):
- 호수, 층, 평수, 타입(select), 월세, 보증금, 옵션(체크박스 여러 개), 메모.

**검증**:
- `react-hook-form` + `zodResolver(createRoomSchema)`.
- 서버 에러(409 중복 호수) → 호수 필드에 인라인 에러 표시.

**성공 시**: 토스트 "등록되었습니다" → `/rooms` 로 이동.

### 1-3. `/rooms/:id` — 상세 페이지

- 모든 필드 읽기 전용 표시.
- 상단에 **상태 변경 드롭다운** — 바로 `changeRoomStatus` 호출.
- 하단에 [수정] [삭제] 버튼.
- 삭제는 confirm dialog 필수 (shared/ui 에 없으면 간단한 컴포넌트 추가).

### 1-4. `/rooms/:id/edit` — 수정 페이지

- 등록 페이지와 동일한 폼, 초기값만 `useRoomQuery(id)` 로 채움.
- 호수는 기본 readonly, "호수 변경" 토글로만 수정 가능 (실수 방지).

`features/room/ui/` 에 신규 생성:

## 4. 검증 체크리스트 (수동 E2E)

- [ ] 로그인 후 `/rooms` 진입 → 층별 카드 뷰(기본값) 표시
- [ ] 뷰 전환 — 층별/칸반/테이블 토글 → URL `?view=...` 반영, 필터 상태 유지
- [ ] 칸반/테이블은 placeholder 메시지 적절히 표시 (MVP)
- [ ] "방 등록" → 신규 등록 → 층별 카드 뷰에 즉시 반영
- [ ] 중복 호수 등록 시 필드 에러 표시 (서버 409 처리)
- [ ] 필터(층/상태) 적용 시 결과 갱신 + URL 반영
- [ ] 상세 → 상태 드롭다운 변경 → 배지 즉시 반영 + 목록도 동기화 (query invalidate)
- [ ] 수정 → 저장 → 상세/목록 반영
- [ ] 삭제 → confirm → 목록에서 제거 (soft delete 검증: 서버 DB 확인)
- [ ] 로그아웃 상태로 `/rooms` 접근 → 로그인 페이지로 리다이렉트

## 5. 이후 구현 예정 (이 문서 범위 외) 🔒

아래 항목들은 **별도 파트에서 다뤄질 예정**이라 이 계획(step1~5)에서는 다루지 않는다:

- **Role 기반 권한 관리**
  - 서버: `User`에 Role 필드 추가, JWT claims 확장, `@PreAuthorize` 적용
  - 프론트: 역할별 메뉴/버튼 노출 제어, 라우트 가드 강화
  - → 현재는 "로그인한 모든 사용자"가 모든 방 관리 기능을 쓸 수 있는 상태로 끝냄
- **입실자 배정 / 계약 관리** — 별도 도메인
- **월세 수납 / 정산** — 별도 도메인
- **방 사진 업로드** — 파일 스토리지 설계 필요
- **건물(Building) 멀티테넌시** — 단일 고시원 전제 해제 시점에 재설계
