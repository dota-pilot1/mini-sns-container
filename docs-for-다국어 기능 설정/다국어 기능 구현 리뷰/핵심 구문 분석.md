# 핵심 구문 분석

## 문서 목적

이 문서는 현재 다국어 구조에서 자주 헷갈리는 핵심 구문이 `왜 가능한지`, `무슨 의미인지`, `왜 이렇게 작성했는지`를 쉽게 설명하기 위한 문서입니다.

특히 아래 구문들을 이해하는 것이 목적입니다.

- `import '@/shared/i18n'`
- `t('namespace:key')`
- `const { t } = useTranslation()`
- `const createLoginSchema = (t: TFunction) => ...`
- `type LoginFormValues = z.infer<ReturnType<typeof createLoginSchema>>`

---

## 1. `import '@/shared/i18n'`

위치:
- [main.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/main.tsx)

코드:

```ts
import '@/shared/i18n'
```

### 의미

이 import는 값을 받아와서 변수처럼 쓰는 import가 아닙니다.  
`i18n 초기화 코드를 실행시키기 위한 import`입니다.

### 왜 필요한가

이 줄이 실행되면 [index.ts](/Users/terecal/mini-sns-conainer/mini-sns-front/src/shared/i18n/index.ts)의 코드가 앱 시작 시 실행됩니다.

즉:
- 언어 리소스 등록
- 기본 언어 설정
- fallback 언어 설정
- namespace 설정
- React와 i18next 연결

이 과정이 끝나야 이후 컴포넌트에서 `useTranslation()`과 `t()`를 정상적으로 사용할 수 있습니다.

### 한 줄 요약

`import '@/shared/i18n'`  
= 다국어 시스템을 앱 시작 시 한 번 부팅하는 코드

## 2. `const { t } = useTranslation()`

예시 위치:
- [login-page.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/routes/login-page.tsx)
- [app-shell.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/shared/layouts/app-shell.tsx)

코드:

```ts
const { t } = useTranslation()
```

### 의미

`react-i18next`에서 번역 함수 `t`를 가져오는 코드입니다.

이 `t`를 사용해서 번역 키를 실제 문자열로 바꿉니다.

예:

```ts
t('common:signIn')
```

이 코드는 현재 언어 기준으로:
- 한국어면 `로그인`
- 영어면 `Sign In`

처럼 바뀝니다.

### 왜 `useTranslation()`을 쓰나

초기화는 `main.tsx`에서 한 번만 하고, 실제 화면에서는 각 컴포넌트에서 `useTranslation()`으로 번역 함수를 가져다 씁니다.

즉:
- 초기화 파일 직접 재사용 X
- 컴포넌트에서는 훅으로 사용 O

## 3. `t('namespace:key')`

예시:

```ts
t('common:signIn')
t('nav:home')
t('auth:login.title')
t('form:errors.invalidEmail')
```

### 구조 분석

형식:

```ts
t('namespace:key')
```

또는 중첩 구조가 있으면:

```ts
t('namespace:parent.child')
```

예:

```ts
t('auth:login.title')
```

의미:
- `auth` namespace 안에서
- `login.title` 값을 찾는다는 뜻

### 왜 이렇게 쓸 수 있나

[index.ts](/Users/terecal/mini-sns-conainer/mini-sns-front/src/shared/i18n/index.ts)에서 아래처럼 namespace를 등록했기 때문입니다.

```ts
ns: ['common', 'nav', 'home', 'auth', 'form']
```

그리고 각 언어 파일에서 namespace별 객체를 export하고 있기 때문에, `t()`가 해당 위치에서 문구를 찾을 수 있습니다.

### 장점

- 공통 문구와 페이지 전용 문구를 분리할 수 있음
- 기능이 늘어날수록 관리가 쉬워짐
- `post`, `comment`, `admin`처럼 계속 확장 가능

## 4. `const createLoginSchema = (t: TFunction) => ...`

위치:
- [login-page.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/routes/login-page.tsx)
- [signup-page.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/routes/signup-page.tsx)

코드:

```ts
const createLoginSchema = (t: TFunction) =>
  z.object({
    email: z.email(t('form:errors.invalidEmail')),
    password: z.string().min(8, t('form:errors.passwordMin')),
  })
```

### 왜 함수로 만들었나

이전에는 이렇게 고정 문자열이었습니다.

```ts
const loginSchema = z.object({
  email: z.email('유효한 이메일을 입력하세요.'),
})
```

문제:
- 메시지가 한국어로 고정
- 언어를 영어로 바꿔도 검증 메시지는 같이 안 바뀜

그래서 스키마를 함수로 바꿔서 `t`를 주입하도록 만든 것입니다.

### 의미

현재 언어 기준으로 번역된 메시지를 스키마 생성 시점에 넣기 위해 함수화했습니다.

즉:
- `t('form:errors.invalidEmail')`
- `t('form:errors.passwordMin')`

이 값이 현재 언어 기준으로 결정됩니다.

### 한 줄 요약

스키마를 함수화한 이유는  
`다국어 에러 메시지를 현재 언어 기준으로 넣기 위해서`입니다.

## 5. `type LoginFormValues = z.infer<ReturnType<typeof createLoginSchema>>`

코드:

```ts
type LoginFormValues = z.infer<ReturnType<typeof createLoginSchema>>
```

### 왜 이렇게 복잡해 보이나

이전에는 스키마가 상수였기 때문에:

```ts
const loginSchema = z.object(...)
type LoginFormValues = z.infer<typeof loginSchema>
```

처럼 단순했습니다.

하지만 지금은 스키마가 함수입니다.

```ts
const createLoginSchema = (t: TFunction) => z.object(...)
```

그래서 먼저:
- `createLoginSchema`가 반환하는 타입을 꺼내고

그 다음:
- 그 반환 타입으로부터 `z.infer`를 해야 합니다.

### 의미를 풀면

1. `typeof createLoginSchema`
   - 함수 자체의 타입

2. `ReturnType<typeof createLoginSchema>`
   - 그 함수가 반환하는 zod schema 타입

3. `z.infer<...>`
   - 그 schema가 검증하는 실제 form value 타입

즉:

```ts
type LoginFormValues = zod 스키마가 최종적으로 만들어내는 form 데이터 타입
```

### 이게 어쩔 수 없는가

어느 정도는 맞습니다.

스키마를 함수화한 순간:
- 타입도 함수 반환 타입을 한 번 거쳐야 하므로
- 표현이 조금 복잡해지는 건 자연스러운 비용입니다.

## 6. `const loginSchema = createLoginSchema(t)`

코드:

```ts
const { t } = useTranslation()
const loginSchema = createLoginSchema(t)
```

### 의미

현재 언어 기준 번역 함수 `t`를 사용해서,  
현재 언어에 맞는 에러 메시지가 들어간 zod schema를 실제로 생성하는 코드입니다.

즉:
- 한국어 상태면 한국어 메시지 스키마
- 영어 상태면 영어 메시지 스키마

가 만들어집니다.

## 7. `i18n.changeLanguage(...)`

위치:
- [language-select.tsx](/Users/terecal/mini-sns-conainer/mini-sns-front/src/shared/ui/language-select.tsx)

코드:

```ts
const { i18n } = useTranslation()

void i18n.changeLanguage(event.target.value)
```

### 의미

사용자가 언어를 선택했을 때 현재 앱 언어를 바꾸는 코드입니다.

이 코드가 실행되면:
- `t()`가 반환하는 값이 바뀌고
- 화면 문구가 새 언어 기준으로 다시 렌더링됩니다.

## 핵심 흐름 한 번에 보기

1. `main.tsx`에서 `import '@/shared/i18n'`
2. i18n 초기화 실행
3. 각 컴포넌트에서 `useTranslation()` 사용
4. `t('namespace:key')`로 문구 출력
5. 언어 선택 시 `changeLanguage(...)` 호출
6. 폼 스키마는 `createSchema(t)`로 생성해서 에러 메시지도 언어에 맞춤

---

## 쉬운 정리

한 줄씩 아주 쉽게 말하면:

- `import '@/shared/i18n'`
  - 다국어 시스템 켜기

- `useTranslation()`
  - 번역 함수 가져오기

- `t('common:signIn')`
  - 번역 키를 실제 문구로 바꾸기

- `createLoginSchema(t)`
  - 현재 언어 기준 에러 메시지로 스키마 만들기

- `z.infer<ReturnType<typeof createLoginSchema>>`
  - 그 스키마가 검증하는 form 값 타입 뽑기

---

## 한 줄 결론

현재 다국어 구조의 핵심은 `앱 시작 시 i18n을 초기화하고, 각 컴포넌트에서는 t()로 문자열을 가져오며, 폼 검증 메시지는 createSchema(t) 방식으로 현재 언어에 맞게 생성하는 것`입니다.
