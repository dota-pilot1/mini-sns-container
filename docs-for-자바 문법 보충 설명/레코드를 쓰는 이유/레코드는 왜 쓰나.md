# 회원 가입 디티오에 레코드를 쓰는 이유는?

```java
package com.cj.stayops.backend.auth.application.dto;

/**
 * 회원가입 유스케이스 입력 DTO.
 * <p>
 * Presentation Layer의 {@code SignupRequest}에서 변환되어 전달된다.
 * raw password를 담으며, UseCase 내부에서 해싱된다.
 */
public record SignupCommand(
	String email,
	String rawPassword,
	String name
) {
}
```

## 간략 설명

### `record`가 뭐냐
Java 16+에서 정식 도입된 **불변 데이터 전용 클래스** 문법. 위 한 줄이 사실상 아래 클래스와 동치다:

```java
public final class SignupCommand {
	private final String email;
	private final String rawPassword;
	private final String name;

	public SignupCommand(String email, String rawPassword, String name) {
		this.email = email;
		this.rawPassword = rawPassword;
		this.name = name;
	}
	public String email() { return email; }
	public String rawPassword() { return rawPassword; }
	public String name() { return name; }

	@Override public boolean equals(Object o) { /* 모든 필드 비교 */ }
	@Override public int hashCode()           { /* 모든 필드 해시 */ }
	@Override public String toString()        { /* 모든 필드 출력 */ }
}
```

컴파일러가 **생성자, 접근자, equals/hashCode/toString**을 자동으로 만들어 준다.

### DTO에 왜 레코드를 쓰나 (5가지 이유)

1. **불변(immutable)**
   - 모든 필드가 `final`. setter 없음.
   - DTO는 "데이터를 옮기는 통"일 뿐 — 중간에 값이 바뀌면 안 됨.
   - 특히 `SignupCommand`처럼 계층 간 이동하는 객체는 불변이 안전.

2. **보일러플레이트 제거**
   - Lombok `@Value`, `@Getter`, `@AllArgsConstructor` 조합이 `record` 한 줄로 끝남.
   - Lombok이라는 외부 의존성 없이 표준 문법으로 해결.

3. **의도가 명확**
   - `class` → "이건 동작(behavior)을 가진 객체야"
   - `record` → "이건 그냥 **데이터 묶음**이야"
   - 읽는 사람이 1초 안에 DTO임을 파악.

4. **equals/hashCode 자동**
   - 테스트에서 `assertEquals(expectedCommand, actualCommand)` 같은 비교가 공짜로 된다.
   - 일반 class로 만들면 IDE로 생성하고 필드 추가할 때마다 재생성해야 함.

5. **접근자 네이밍이 간결**
   - `getEmail()` 이 아니라 `email()`.
   - JavaBeans 스타일 getter는 "객체 상태를 가져오는 메서드"라는 뉘앙스, record의 접근자는 "컴포넌트 값 그 자체"라는 뉘앙스.

### 언제 레코드를 쓰면 안 되는가
- **상태 변경이 필요한 객체** (예: 도메인 Aggregate Root인 `User` — 나중에 이메일 변경 등 동작 필요)
- **상속이 필요한 경우** (record는 `final` 고정)
- **JPA 엔티티** (JPA가 기본 생성자 + setter를 요구함 → `UserJpaEntity`는 일반 class로 둔 이유)

그래서 이 프로젝트에서도:
- DTO (`SignupCommand`, `SignupResult`, `SignupRequest`, `SignupResponse`, `ErrorResponse`) → **record**
- 도메인 Aggregate (`User`) / JPA Entity (`UserJpaEntity`) → **class**
- 식별자 VO (`UserId`, `Email`) → class (생성자 검증 로직과 정적 팩토리 필요해서 record보다 class가 깔끔)

### 이 파일(`SignupCommand`)에 적용된 것
```java
public record SignupCommand(String email, String rawPassword, String name) {}
```
- 3개 필드 모두 `final` 불변
- `command.email()`, `command.rawPassword()`, `command.name()` 으로 조회
- Application Layer 진입 시 Presentation의 `SignupRequest.toCommand()`에서 생성되고, UseCase 내부에서 소비된 뒤 사라짐 → **짧은 수명의 데이터 통**에 딱 맞는 구조.
