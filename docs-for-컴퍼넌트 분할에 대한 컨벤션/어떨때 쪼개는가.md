# 컴포넌트 분할 컨벤션: 어떨 때 쪼개는가


## 기본 원칙
===================================================================
"쪼개는 게 이득인가?" 를 기준으로 판단한다.
파일을 나누면 코드 탐색 비용이 생기고,
합쳐두면 파일이 길어지는 비용이 생긴다.
둘 중 더 싼 쪽을 선택.
===================================================================


## 쪼개야 하는 4가지 조건 (하나라도 해당하면 분리)

### 조건 1: 다른 곳에서도 쓴다 (재사용)
===================================================================
NavLink 을 AppShell 에서만 쓰면 → 같은 파일에 둬도 됨
NavLink 을 Sidebar, Footer 등 여러 곳에서 쓰면 → 분리
===================================================================
→ 재사용 = 파일 분리의 가장 강한 이유.
→ 한 곳에서만 쓰이는 컴포넌트를 억지로 쪼개면 파일만 늘어남.


### 조건 2: 파일이 300줄을 넘는다
===================================================================
~170줄: 한 화면에 다 보임 → 안 쪼개도 됨
~300줄: 스크롤 시작 → 쪼갤지 고민
~500줄+: 반드시 쪼개기 → 읽기 비용 > 파일 왔다갔다 비용
===================================================================
→ 300줄은 경험적 기준. 절대적인 숫자는 아니지만 실무에서 많이 쓰이는 마지노선.
→ 줄 수 자체보다 "한눈에 전체 구조가 파악되는가" 가 본질.


### 조건 3: 독립적으로 테스트하고 싶다
===================================================================
UserMenu 를 단독 유닛 테스트 하고 싶다 → 분리하면 테스트 파일도 깔끔
UserMenu 가 단순해서 E2E 로 충분하다 → 굳이 분리 안 해도 됨
===================================================================
→ 자체 상태(useState, useRef, useEffect)가 복잡할수록 단독 테스트 가치가 올라감.
→ 지금 UserMenu 는 open/close 하나라 E2E 수준이면 충분.


### 조건 4: 여러 사람이 동시에 수정한다 (팀 협업)
===================================================================
1인 프로젝트 → 충돌 없음 → 합쳐둬도 무방
팀에서 한 명은 UserMenu, 한 명은 NavLink 작업 → 같은 파일 = git 충돌
===================================================================
→ 팀 규모가 커질수록 파일 분리 기준이 낮아짐 (200줄 이상이면 쪼개는 팀도 있음).
→ 1인이면 편한 대로.


## 쪼개지 말아야 할 때

### 안티패턴: 10줄짜리를 별도 파일로
===================================================================
// logout-icon.tsx  ← 15줄짜리 SVG 아이콘 하나를 위한 파일
export function LogoutIcon() { ... }
===================================================================
→ 이 아이콘을 찾으려면 파일 트리를 뒤져야 됨.
→ UserMenu 안에 같이 두면 "여기서 쓰는 아이콘이구나" 즉시 파악.
→ 아이콘이 10개 이상 모이면 그때 icons/ 폴더로 분리하는 게 자연스러움.


### 안티패턴: "컴포넌트 = 파일" 강박
===================================================================
app-shell.tsx      ← 40줄
user-menu.tsx      ← 50줄
nav-link.tsx       ← 20줄
logout-icon.tsx    ← 15줄
===================================================================
→ 4파일 합쳐도 125줄. 한 파일이면 한눈에 보이는 양을 4번 왔다갔다.
→ "모든 컴포넌트는 각자 파일" 규칙은 대규모 프로젝트에서나 의미 있음.


## 실전 판단 플로우

```
파일 줄 수 > 300?
  ├─ YES → 쪼개기
  └─ NO
       ├─ 다른 곳에서도 쓰는 컴포넌트 있음? → 그것만 분리
       ├─ 단독 테스트 필요? → 그것만 분리
       ├─ 팀원과 동시 수정 빈번? → 쪼개기
       └─ 전부 NO → 그대로 두기
```


## 나중에 쪼개는 것도 OK

===================================================================
처음부터 완벽하게 분리하려고 에너지 쓰지 말 것.
"나중에 필요해지면 그때 쪼개면 된다" 가 실용적 접근.
===================================================================
→ 리팩터링 비용은 처음부터 과분리 하는 비용보다 대체로 낮음.
→ IDE 의 "Move to new file" 기능으로 10초면 끝남.
→ 핵심은 "지금 이 분리가 읽기/유지보수를 실제로 편하게 만드는가?" 를 매번 자문.


## 한 줄 요약
===================================================================
"재사용 없고, 300줄 안 넘고, 테스트 단독 불필요하고, 혼자 작업이면 → 안 쪼갠다.
 하나라도 해당하면 → 해당하는 것만 쪼갠다."
===================================================================
