# 핵심 개념: JwtAuthenticationFilter 를 Spring Security 필터 체인에 끼워 넣기
===================================================================
원래 Spring Security 필터 체인은 이렇게 흐름:

HTTP 요청
  ↓
[SecurityContextPersistenceFilter]
[CorsFilter]
[CsrfFilter]
[UsernamePasswordAuthenticationFilter]   ← 폼 로그인용 (우린 안 씀)
[ExceptionTranslationFilter]             ← EntryPoint 발동 주체
[FilterSecurityInterceptor]              ← authenticated() 판정
  ↓
컨트롤러

여기 사이에 우리가 만든 JwtAuthenticationFilter 를 끼워서,
"요청마다 토큰 검사 → SecurityContext 채우기" 역할을 맡긴다.
===================================================================


Step1: SecurityConfig 에서 필터를 꽂는다 (step6 에서 진행 예정)
===================================================================
@Configuration
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;
    private final RestAuthenticationEntryPoint entryPoint;

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(sm -> sm.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/users/**").authenticated()   // ← 보호
                .anyRequest().authenticated()
            )
            .exceptionHandling(eh -> eh
                .authenticationEntryPoint(entryPoint)               // ← 401 응답 책임자
            )
            .addFilterBefore(                                       // ← 필터 끼우는 지점
                jwtAuthenticationFilter,
                UsernamePasswordAuthenticationFilter.class
            )
            .build();
    }
}
===================================================================
3가지를 한 번에 선언:
  (1) 어떤 경로를 permitAll / authenticated 로 할지
  (2) 인증 실패 시 EntryPoint 로 401 내리기
  (3) 체인에 우리 필터 삽입


Step2: 핵심 구문 — 필터를 "어디" 꽂는가
===================================================================
.addFilterBefore(
    jwtAuthenticationFilter,
    UsernamePasswordAuthenticationFilter.class
)
===================================================================
뜻: "UsernamePasswordAuthenticationFilter 바로 앞 자리에
     jwtAuthenticationFilter 를 꽂아라."

왜 이 위치?
→ 폼 로그인이 인증 정보를 읽는 타이밍 바로 앞에서,
  우리가 JWT 로 SecurityContext 를 먼저 채워주는 구조.
→ 결과적으로 UsernamePasswordAuthenticationFilter 는
  이미 인증된 상태를 보고 아무것도 안 하고 통과.


Step3: 필터 동작 시나리오
===================================================================
[Case A] GET /api/users (토큰 있음, 유효)
  → 필터: 검증 OK → SecurityContext 세팅
  → 인가: authenticated() 통과
  → 200 OK

[Case B] GET /api/users (토큰 없음)
  → 필터: 헤더 없음 → SecurityContext 비어있음
  → 인가: authenticated() 실패
  → EntryPoint → 401 JSON

[Case C] GET /api/users (토큰 만료/위조)
  → 필터: catch → SecurityContext 비움 (응답 안 건드림)
  → 인가: authenticated() 실패
  → EntryPoint → 401 JSON

[Case D] POST /api/auth/login (토큰 있든 없든)
  → 필터: (검증하든 말든)
  → 인가: /api/auth/** 는 permitAll → 통과
  → AuthController.login 도달 → 토큰 발급
===================================================================
유저 목록 요청 시 → 토큰 있으면 통과, 없으면 401.
로그인 요청 시 → 필터 결과와 무관하게 컨트롤러까지 도달.
이유: FilterSecurityInterceptor 가 /api/auth/** 를 permitAll 로 판정해서.


한 줄 요약
===================================================================
"필터는 SecurityContext 채우기만, 허용/거부 판정은 인가 필터,
 거부 시 응답 내리기는 EntryPoint — 3자 분업 구조."
