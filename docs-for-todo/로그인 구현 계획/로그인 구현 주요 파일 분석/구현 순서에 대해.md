좋은 메타 질문. 구현 순서 와 이해 순서 는 다르게 가는 게 정답임.

구현 순서: 안에서 밖으로 (지금 방식)
Domain → UseCase → Controller
왜 이 순서가 안정적인가

타입이 아래에서 위로 확정됨. LoginResult 가 있어야 컨트롤러가 뭘 리턴할지 확정 가능.
컴파일이 계속 성공함. 위에서 시작하면 LoginUseCase 가 아직 없어서 목/스텁 깔아야 됨 → 나중에 실제 구현으로 갈아끼울 때 한 번 더 흔들림.
테스트 짜기 쉬움. UseCase 는 HTTP 없이 순수 함수처럼 테스트 가능 → 비즈니스 규칙(비번 불일치 시 어떻게?)을 먼저 확정.
DDD 구조(이 프로젝트)에선 도메인이 중심이라 이 방향이 결대로임.
이해 순서: 밖에서 안으로 (읽는 관점)
Controller → UseCase → Domain
왜 이 순서가 직관적인가

HTTP 요청이 도착해서 "어디로 흘러가는지" 를 따라가는 게 인간 멘탈 모델과 일치.
"POST /api/auth/login 이 뭐 하는 놈이지?" → 컨트롤러 열어서 → UseCase 호출 보고 → UseCase 열어서 → 레포지토리/토큰 프로바이더 보고 → 도메인.
실무 관례
두 방식 다 존재:

Inside-out (도메인 우선) — DDD/헥사고날 진영. 지금 이 프로젝트.
Outside-in (API 우선) — "API-first 개발", OpenAPI 스펙부터 찍고 내려오기. 프론트팀과 계약 먼저 확정해야 할 때 유리.
한쪽이 옳은 게 아니라 팀 문화/프로젝트 성격에 따라 선택. 이 프로젝트는 DDD 구조 + 이미 Signup 도 같은 순서로 갔었음 (SignupUseCase → AuthController) → 일관성 유지 차원에서도 유지하는 게 맞음.

너한테 추천하는 방식
구현할 때: 지금처럼 아래부터 (타입·테스트 안정성).
코드 읽고 이해할 때: Controller → UseCase → Domain 순으로 거꾸로.

즉 step4 (Controller) 가 끝나면, 그때 한 번 "엔드포인트부터 추적" 으로 전체 흐름을 다시 훑어보는 게 이해에 도움됨. 지금 LoginUseCase.java 만 외따로 읽으면 "이게 누가 호출하지?" 가 공백으로 남아서 덜 와닿음.

step4 먼저 끝내고 그 시점에 "엔드포인트 → 유스케이스 → 토큰 프로바이더 → 도메인" 전체 흐름 한 번 같이 훑는 걸 추천. ㄱㄱ?
