# Presentation 계층 설명

## 1. 한 줄 정의

> **"외부 세계(HTTP, CLI, 메시지 큐 등)와 애플리케이션이 만나는 접점"**
> 요청을 받아 UseCase를 호출하고, 결과/예외를 외부 형식으로 변환한다.

현재 프로젝트에서는 **HTTP REST API**를 다루는 Web Presentation이 있음.

## 2. 여기에 들어가는 것

| 종류 | 예시 (auth) | 설명 |
|---|---|---|
| **Controller** | `AuthController` | HTTP 엔드포인트 (`@RestController`) |
| **Request DTO** | `SignupRequest` | HTTP 요청 바디 (Bean Validation) |
| **Response DTO** | `SignupResponse` | HTTP 응답 바디 |
| **Error DTO** | `ErrorResponse` | 에러 응답 규격 |
| **Exception Handler** | `AuthExceptionHandler` | 예외 → HTTP 응답 변환 |
| *(확장 시)* Interceptor, Filter | 인증/로깅 미들웨어 | HTTP 전처리 |

## 3. 실제 패키지 구조

```
auth/presentation/
├── dto/
│   ├── SignupRequest.java      ← HTTP 요청 바디
│   ├── SignupResponse.java     ← HTTP 응답 바디
│   └── ErrorResponse.java      ← 에러 응답 공통
├── AuthController.java         ← @RestController
└── AuthExceptionHandler.java   ← @RestControllerAdvice
```

## 4. 핵심 코드 발췌

### AuthController — Thin Controller

```java
@RestController
@RequestMapping("/api/auth")
@Tag(name = "Auth", description = "인증/회원가입 API")
public class AuthController {

    private final SignupUseCase signupUseCase;

    public AuthController(SignupUseCase signupUseCase) {
        this.signupUseCase = signupUseCase;
    }

    @PostMapping("/signup")
    @Operation(summary = "회원가입", description = "이메일/비밀번호/이름을 받아 신규 사용자를 등록합니다.")
    @ApiResponses({
        @ApiResponse(responseCode = "201", description = "가입 성공"),
        @ApiResponse(responseCode = "400", description = "형식 오류"),
        @ApiResponse(responseCode = "409", description = "이메일 중복")
    })
    public ResponseEntity<SignupResponse> signup(@Valid @RequestBody SignupRequest request) {
        SignupResult result = signupUseCase.execute(request.toCommand());
        return ResponseEntity.status(HttpStatus.CREATED).body(SignupResponse.from(result));
    }
}
```

**포인트**
- `@RestController` — JSON 응답 자동
- `@RequestMapping("/api/auth")` — 공통 경로 prefix
- **메서드 본문 3줄**: 요청 변환 → UseCase 호출 → 응답 변환
- `@Valid` — Bean Validation 1차 검증
- OpenAPI 어노테이션(`@Tag`, `@Operation`, `@ApiResponses`) — Swagger 자동 생성

### SignupRequest — Bean Validation + Swagger

```java
@Schema(description = "회원가입 요청")
public record SignupRequest(

    @Schema(description = "이메일", example = "user@example.com", maxLength = 254)
    @NotBlank(message = "email must not be blank")
    @Email(message = "email format is invalid")
    @Size(max = 254)
    String email,

    @Schema(description = "비밀번호 (영문+숫자, 8~72자)", example = "password123")
    @NotBlank(message = "password must not be blank")
    @Size(min = 8, max = 72)
    String password,

    @Schema(description = "사용자 이름", example = "홍길동", maxLength = 100)
    @NotBlank(message = "name must not be blank")
    @Size(max = 100)
    String name
) {
    public SignupCommand toCommand() {
        return new SignupCommand(email, password, name);
    }
}
```

**포인트**
- `record` — 불변 DTO (setter 없음)
- Bean Validation 어노테이션 — HTTP 진입 시 자동 검증
- `toCommand()` — **계층 경계 변환 메서드** (HTTP → UseCase 입력)
- `@Schema` — Swagger 문서에 설명 자동 반영

### SignupResponse — 응답 DTO

```java
public record SignupResponse(
    String userId,
    String email,
    String name,
    Instant createdAt
) {
    public static SignupResponse from(SignupResult result) {
        return new SignupResponse(
            result.userId(), result.email(), result.name(), result.createdAt()
        );
    }
}
```

**포인트**
- UseCase의 `SignupResult`와 구조가 거의 같아도 **별도 클래스**
- 이유: HTTP 응답 형식은 독립적 진화 필요 (필드 rename, 구조 변경, 버저닝 등)

### ErrorResponse — 에러 응답 공통 규격

```java
public record ErrorResponse(
    String code,
    String message,
    List<FieldError> errors,
    Instant timestamp
) {
    public static ErrorResponse of(String code, String message) {
        return new ErrorResponse(code, message, List.of(), Instant.now());
    }

    public static ErrorResponse of(String code, String message, List<FieldError> errors) {
        return new ErrorResponse(code, message, errors, Instant.now());
    }

    public record FieldError(String field, String message) {}
}
```

**포인트**
- 모든 에러 응답이 같은 구조 → 프론트에서 일관된 파싱
- `code`로 분기 (`DUPLICATE_EMAIL`, `VALIDATION_FAILED` 등)
- `errors` 리스트로 필드별 오류 상세

### AuthExceptionHandler — 예외 → HTTP 변환

```java
@RestControllerAdvice(basePackages = "com.cj.stayops.backend.auth.presentation")
public class AuthExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        List<ErrorResponse.FieldError> fieldErrors = e.getBindingResult().getFieldErrors().stream()
            .map(fe -> new ErrorResponse.FieldError(fe.getField(), fe.getDefaultMessage()))
            .toList();
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(ErrorResponse.of("VALIDATION_FAILED", "Request validation failed", fieldErrors));
    }

    @ExceptionHandler(DuplicateEmailException.class)
    public ResponseEntity<ErrorResponse> handleDuplicateEmail(DuplicateEmailException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(ErrorResponse.of("DUPLICATE_EMAIL", e.getMessage()));
    }

    @ExceptionHandler(InvalidEmailException.class)
    public ResponseEntity<ErrorResponse> handleInvalidEmail(InvalidEmailException e) { /* 400 */ }

    @ExceptionHandler(WeakPasswordException.class)
    public ResponseEntity<ErrorResponse> handleWeakPassword(WeakPasswordException e) { /* 400 */ }
}
```

**포인트**
- `@RestControllerAdvice(basePackages = "...")` — **auth 패키지에만 적용**
- 나중에 전역화할 때 `shared/presentation/GlobalExceptionHandler`로 승격
- **도메인 예외**(`DuplicateEmailException` 등)를 **HTTP 상태 코드**로 변환
- 에러 코드 체계화 (`DUPLICATE_EMAIL`, `VALIDATION_FAILED`, ...)

## 5. HTTP 상태 코드 매핑

| 상황 | HTTP | 에러 코드 |
|---|---|---|
| 가입 성공 | **201 Created** | - |
| Bean Validation 실패 (형식) | **400** | `VALIDATION_FAILED` |
| 이메일 형식 (도메인) | **400** | `INVALID_EMAIL` |
| 비밀번호 정책 | **400** | `WEAK_PASSWORD` |
| 이메일 중복 | **409 Conflict** | `DUPLICATE_EMAIL` |
| *(예정)* 인증 실패 | 401 | `INVALID_CREDENTIALS` |
| *(예정)* 권한 부족 | 403 | `FORBIDDEN` |
| *(예정)* 리소스 없음 | 404 | `NOT_FOUND` |
| 서버 오류 (fallback) | 500 | `INTERNAL_ERROR` |

## 6. Thin Controller 원칙

Controller 메서드 본문은 **3줄 이내**가 이상적:

```java
public ResponseEntity<XxxResponse> doSomething(@Valid @RequestBody XxxRequest request) {
    XxxResult result = xxxUseCase.execute(request.toCommand());
    return ResponseEntity.status(...).body(XxxResponse.from(result));
}
```

**Controller에 있어야 할 것**
- ✅ HTTP 메서드/경로 매핑 (`@PostMapping`)
- ✅ 요청 바인딩/검증 (`@Valid @RequestBody`)
- ✅ UseCase 호출
- ✅ HTTP 응답 생성 (상태 코드, 헤더)
- ✅ OpenAPI 문서화 어노테이션

**Controller에 있으면 안 될 것**
- ❌ 비즈니스 규칙 (정규식 체크, 비교 로직)
- ❌ DB 접근
- ❌ 여러 UseCase를 조합하는 로직 (→ 새 UseCase 만들기)
- ❌ 트랜잭션 제어

## 7. DTO 4개의 흐름 (Request → Response)

```
[브라우저]
  JSON ──────────────────────────────► SignupRequest
                                            │
                              .toCommand() │
                                            ▼
                                      SignupCommand
                                            │
                               UseCase.execute() │
                                            ▼
                                      SignupResult
                                            │
                              SignupResponse.from() │
                                            ▼
                                      SignupResponse ──► JSON
[브라우저]
```

**계층 경계마다 DTO 변환** → 각 계층 독립적으로 진화 가능.

## 8. OpenAPI (Swagger) 통합

현재 프로젝트는 **springdoc-openapi 2.8.6** 사용:
- UI: `http://localhost:8080/swagger-ui/index.html`
- JSON: `http://localhost:8080/v3/api-docs`

**어노테이션**
| 어노테이션 | 위치 | 용도 |
|---|---|---|
| `@Tag` | Controller 클래스 | API 그룹 이름/설명 |
| `@Operation` | 메서드 | 개별 API 요약/설명 |
| `@ApiResponses` | 메서드 | 응답 코드별 설명 |
| `@Schema` | DTO 클래스/필드 | 스키마 설명, 예시 값 |

**보안 설정**
SecurityConfig에서 Swagger 경로를 permitAll:
```java
.requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll()
```

## 9. 자주 하는 질문

### Q. `@Valid` vs 도메인 검증 둘 다 있는데 중복 아닌가?
**아니다. 역할이 다름.**
- `@Valid` (Bean Validation): **HTTP 경계의 빠른 거절** (형식, 길이)
- `Email.of()` (도메인): **비즈니스 규칙의 엄격한 검증** (정규식, 정규화)

1차 방어로 빠르게 걸러내고, 통과한 것만 도메인에서 최종 검증.

### Q. Controller 테스트는 어떻게?
- **@WebMvcTest**: Controller만 띄우고 UseCase는 mock → 빠름
- **@SpringBootTest + MockMvc**: 전체 컨텍스트 → 통합 테스트용
- 대부분 `@WebMvcTest`로 충분 (HTTP 파싱, 상태코드, 예외 변환만 검증)

### Q. 응답 포맷을 `{success, data}`로 감싸야 하나?
팀 취향. 장단점:
- **Raw 방식** (현재): 리소스 직접 반환 → 가볍고 RESTful
- **Envelope 방식** (`{success, data, error}`): 일관성 있지만 중복 정보 많음

GraphQL이나 RPC-like API는 envelope 선호, REST는 raw 선호 경향.

### Q. Controller를 여러 개 나눌지 하나로 뭉칠지?
**도메인별로 하나씩**. 이 프로젝트는 auth 도메인 → `AuthController`.
앞으로 `ReservationController`, `RoomController`, `PaymentController` 등 생길 예정.

### Q. 전역 예외 처리는 언제 만드나?
**공통 패턴이 보일 때.** 지금은 auth 전용 핸들러 1개. 로그인/이메일인증/비밀번호재설정 등이 추가되면:
1. 공통 `DomainException` 베이스 클래스 도입
2. `shared/presentation/GlobalExceptionHandler`로 승격
3. auth 핸들러 제거

**조기 추상화 금지** — 패턴이 명확할 때 추출.

### Q. `@RestController` vs `@Controller` + `@ResponseBody`?
`@RestController`가 **둘을 합친 어노테이션**. REST API면 `@RestController`만 쓰면 됨.
`@Controller`는 뷰(Thymeleaf 등) 렌더링용.

### Q. Presentation에서 Domain을 import해도 되나?
**예외 타입만** OK (exception handler 작성용).
**도메인 객체(User, Email)를 Controller에서 직접 쓰면 안 됨** — 반드시 DTO 변환.

## 10. 한 줄 요약

> **Presentation = "외부 세계의 언어(HTTP)를 애플리케이션의 언어(UseCase)로 번역하는 창구"**.
> Controller는 얇게, 검증은 Bean Validation + Domain 이중으로, 예외는 구조화된 JSON으로.
