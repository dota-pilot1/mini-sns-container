# Application 계층 설명

## 1. 한 줄 정의

> **"비즈니스 시나리오를 조율(orchestrate)하는 곳"**
> 규칙 자체는 Domain에 있고, Application은 **"어떤 순서로 무엇을 호출할지"**를 정의한다.

## 2. 여기에 들어가는 것

| 종류 | 예시 (auth) | 설명 |
|---|---|---|
| **UseCase** | `SignupUseCase` | 하나의 비즈니스 시나리오 실행 |
| **Command DTO** | `SignupCommand` | UseCase 입력 (HTTP 몰라도 됨) |
| **Result DTO** | `SignupResult` | UseCase 출력 (도메인 객체 노출 방지) |
| *(나중에)* Query | `FindUserByIdQuery` | 읽기 전용 조회 (CQRS) |
| *(나중에)* Application Service | `JwtTokenService` 인터페이스 등 | 여러 UseCase 공유 로직 |

## 3. 실제 패키지 구조

```
auth/application/
├── dto/
│   ├── SignupCommand.java    ← 입력
│   └── SignupResult.java     ← 출력
└── SignupUseCase.java        ← @Service @Transactional
```

## 4. 핵심 코드 발췌

### SignupUseCase — 조율의 실체

```java
@Service
public class SignupUseCase {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final Clock clock;

    public SignupUseCase(UserRepository userRepository,
                         PasswordEncoder passwordEncoder,
                         Clock clock) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
        this.clock = clock;
    }

    @Transactional
    public SignupResult execute(SignupCommand command) {
        // ========== 1단계: 유효성 검증 ==========
        Email email = Email.of(command.email());              // (1-1) Domain VO가 형식 검증
        validatePasswordPolicy(command.rawPassword());         // (1-2) 앱 정책
        if (userRepository.existsByEmail(email)) {             // (1-3) 중복 체크
            throw new DuplicateEmailException(email.value());
        }

        // ========== 2단계: 도메인 객체 생성 ==========
        String passwordHash = passwordEncoder.encode(command.rawPassword());
        Instant now = Instant.now(clock);
        User user = User.register(UserId.generate(), email, passwordHash,
                                  command.name(), now);

        // ========== 3단계: 영속화 및 결과 반환 ==========
        User saved = userRepository.save(user);
        return SignupResult.from(saved);
    }
}
```

**포인트**
- `@Service` — Spring 빈으로 등록
- `@Transactional` — 메서드 전체가 하나의 트랜잭션
- **생성자 주입** — 필드 `final`, 테스트 시 의존성 교체 용이
- `Clock` 주입 — `Instant.now()` 직접 호출 X, 테스트에서 시간 고정 가능

### SignupCommand — 입력 DTO (record)

```java
public record SignupCommand(
    String email,
    String rawPassword,   // 아직 해시 안 된 원본
    String name
) {
}
```

**포인트**
- HTTP와 무관 — Bean Validation 어노테이션 없음
- `rawPassword`라는 이름으로 "아직 해시 안 됨" 명시
- CLI, Kafka, 테스트 등 **어떤 입력 채널에서도 사용 가능**

### SignupResult — 출력 DTO

```java
public record SignupResult(
    String userId,
    String email,
    String name,
    Instant createdAt
) {
    public static SignupResult from(User user) {
        return new SignupResult(
            user.id().asString(),
            user.email().value(),
            user.name(),
            user.createdAt()
        );
    }
}
```

**포인트**
- `User` 도메인 객체를 직접 반환하지 않음 (`passwordHash` 노출 방지)
- `from()` 정적 팩토리로 변환 로직을 한 곳에 집중
- UUID는 `String`으로 노출 (언어 독립적)

## 5. Application vs Domain 경계

| | Application | Domain |
|---|---|---|
| 담는 것 | **흐름/순서** | **규칙/개념** |
| 예시 | "회원가입은 이메일 검증 → 중복체크 → 저장 순서로" | "이메일이란 X@Y.Z 형식이다" |
| 바뀔 때 | 시나리오가 바뀔 때 | 비즈니스 규칙이 바뀔 때 |
| 기술 의존 | Spring, JPA 참조 가능 | 금지 |

**헷갈릴 때 판단 기준**
- "이 코드를 HTTP 아닌 CLI에서도 그대로 쓸 수 있나?" → **Application에 두기 적합**
- "이 규칙은 언제 어디서든 지켜져야 하나?" → **Domain에 두기 적합**

## 6. Thin Controller / Fat Service의 함정 피하기

전통적 Spring에서 흔한 실수:
```java
// ❌ Fat Service - 도메인 규칙이 Service에 흩어짐
@Service
public class UserService {
    public void signup(String email, String pw, String name) {
        if (!email.matches(EMAIL_REGEX)) throw ...;  // 규칙이 여기 있네
        if (pw.length() < 8) throw ...;              // 규칙이 여기도
        User user = new User();
        user.setEmail(email.toLowerCase());           // 정규화도 여기
        user.setPassword(encoder.encode(pw));
        userRepository.save(user);
    }
}
```

**문제**: 같은 이메일 규칙을 로그인, 이메일 변경 등에서 **복붙**하게 됨.

**DDD 방식**:
```java
// ✅ 규칙은 Domain VO에 집중
Email email = Email.of(rawEmail);   // 규칙은 Email이 책임
// Application은 "어떤 순서로 호출할지"만 담당
```

## 7. UseCase 설계 원칙

### 원칙 1. 하나의 UseCase = 하나의 시나리오
- `SignupUseCase` — 가입만
- `LoginUseCase` — 로그인만 (따로)
- `ChangePasswordUseCase` — 비번 변경만 (따로)

**반대**: `AuthService`에 signup/login/changePassword 다 몰아넣기 → 클래스 비대화

### 원칙 2. public 메서드는 `execute()` 하나
- 클래스 이름이 이미 의도를 전달 (`SignupUseCase`)
- `execute(command)` 단일 진입점 → 일관성

### 원칙 3. 트랜잭션 경계는 UseCase
- `@Transactional`은 UseCase의 `execute()`에 붙음
- Controller나 Repository에 붙이지 않음
- **"하나의 시나리오 = 하나의 트랜잭션"** 원칙

### 원칙 4. 도메인 인터페이스만 의존
- `UserRepository` (도메인 인터페이스) ✅
- `UserJpaRepository` (Spring Data) ❌
- Spring의 표준 인터페이스(`PasswordEncoder`)는 예외적으로 허용 가능

## 8. Command vs Request 네이밍

| 이름 | 계층 | 관심사 |
|---|---|---|
| `SignupRequest` | Presentation | HTTP 요청 (Bean Validation 포함) |
| `SignupCommand` | Application | UseCase 입력 (HTTP 무관) |

**왜 둘 다 두나**
- Application이 HTTP/Bean Validation에 오염되지 않게
- CLI, Kafka, 테스트 등에서 UseCase 재사용 가능
- 계층 경계에서 변환 (`SignupRequest.toCommand()`)

**CQRS 패턴의 Command = "상태 변경 의도"**.
Query는 읽기 전용 (예: `FindUserByEmailQuery`).

## 9. 자주 하는 질문

### Q. UseCase에 여러 메서드를 둬도 되나?
원칙적으론 `execute()` 하나. 예외:
- private helper 메서드는 OK (`validatePasswordPolicy` 등)
- 드물게 "아주 밀접한 보조 시나리오"가 있으면 같은 클래스에 두는 경우도 있음

헷갈리면 **분리**가 정답.

### Q. 왜 `SignupService`가 아니고 `SignupUseCase`인가?
네이밍 선택. 의미는 같음:
- `XxxService` — Spring 전통 스타일
- `XxxUseCase` — DDD/Clean Architecture 스타일 (의도 더 명확)
- `XxxApplicationService` — 풀 DDD 스타일

팀에서 합의된 이름이면 뭐든 OK. 본 프로젝트는 `UseCase` 사용.

### Q. Application이 Spring 어노테이션을 써도 되나?
**Yes**. `@Service`, `@Transactional` 등은 Application에 자연스럽게 들어감.
Domain만 Spring 금지. Application은 "기술 + 도메인의 다리" 역할이라 양쪽 허용.

### Q. 여러 UseCase가 공통 로직을 쓰면?
- 작은 유틸: private 메서드 복사 허용
- 중간 규모: 별도 `application/` 하위 공통 클래스
- 도메인 수준 로직: **Domain Service로 격상** (도메인 계층으로 이동)

## 10. 한 줄 요약

> **Application = "시나리오 지휘자"**.
> Domain 객체들을 조합해서 "회원가입은 이렇게 진행한다"를 코드로 표현.
> 규칙은 Domain이 알고, 순서는 Application이 안다.
