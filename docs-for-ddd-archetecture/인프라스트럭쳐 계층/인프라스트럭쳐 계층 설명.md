# Infrastructure 계층 설명

## 1. 한 줄 정의

> **"Domain이 필요로 하는 기술을 실제로 구현하는 곳"**
> DB, 외부 API, 메시지 큐, 파일 저장소 등 **외부 세계와 통신하는 모든 기술 구현**이 여기 모인다.

## 2. 여기에 들어가는 것

| 종류 | 예시 (현재/예정) | 설명 |
|---|---|---|
| **JPA Entity** | `UserJpaEntity` | DB 테이블 매핑 (`@Entity`) |
| **Spring Data Repository** | `UserJpaRepository` | `JpaRepository` 상속 |
| **Domain Repository 구현체** | `UserRepositoryImpl` | 도메인 계약 + JPA 어댑터 |
| *(예정)* JWT Provider | `JwtTokenProviderImpl` | 토큰 발급/검증 |
| *(예정)* Mail Sender | `SmtpEmailSenderImpl` | 이메일 발송 |
| *(예정)* Cache | `RedisCacheImpl` | Redis 어댑터 |
| *(예정)* External API Client | `SlackNotifierImpl` | 외부 서비스 호출 |

## 3. 실제 패키지 구조

```
auth/infrastructure/
└── persistence/
    ├── UserJpaEntity.java       ← @Entity (DB 테이블)
    ├── UserJpaRepository.java   ← Spring Data JPA
    └── UserRepositoryImpl.java  ← UserRepository 구현
```

**향후 확장 예시**
```
auth/infrastructure/
├── persistence/    ← DB
├── security/       ← JWT, 토큰 저장소
├── mail/           ← SMTP/SendGrid
├── cache/          ← Redis
├── messaging/      ← Kafka Producer
└── external/       ← OAuth Provider, OTP Sender 등
```

## 4. 핵심 코드 발췌

### UserJpaEntity — JPA 영속화 전용 엔티티

```java
@Entity
@Table(name = "users", indexes = {
    @Index(name = "uk_users_email", columnList = "email", unique = true)
})
public class UserJpaEntity {

    @Id
    @Column(name = "id", columnDefinition = "uuid", nullable = false, updatable = false)
    private UUID id;

    @Column(name = "email", nullable = false, length = 254, unique = true)
    private String email;

    @Column(name = "password_hash", nullable = false, length = 100)
    private String passwordHash;

    @Column(name = "name", nullable = false, length = 100)
    private String name;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    protected UserJpaEntity() {}  // JPA 기본 생성자

    public UserJpaEntity(UUID id, String email, String passwordHash, String name,
                         Instant createdAt, Instant updatedAt) { /* ... */ }

    // getter만 제공 (setter 없음)
}
```

**포인트**
- **도메인 `User`와 완전히 분리된 클래스** (JPA 제약을 도메인에 안 섞기 위함)
- `@Entity`, `@Table`, `@Column`, `@Index` 전부 여기에만 존재
- PostgreSQL `uuid` 네이티브 타입 사용 (`columnDefinition = "uuid"`)
- **unique index** 로 이메일 중복 최후 방어선
- 기본 생성자 `protected` — 외부 생성 차단, JPA만 사용

### UserJpaRepository — Spring Data JPA

```java
public interface UserJpaRepository extends JpaRepository<UserJpaEntity, UUID> {
    Optional<UserJpaEntity> findByEmail(String email);
    boolean existsByEmail(String email);
}
```

**포인트**
- 메서드 이름만으로 SQL 자동 생성:
  - `findByEmail(...)` → `SELECT ... WHERE email = ?`
  - `existsByEmail(...)` → `SELECT EXISTS(... WHERE email = ?)`
- `save`, `findById`, `delete` 등은 `JpaRepository`가 기본 제공
- **도메인 계층은 이 인터페이스를 모름** — `UserRepositoryImpl` 내부에서만 사용

### UserRepositoryImpl — 도메인 ↔ JPA 어댑터

```java
@Repository
public class UserRepositoryImpl implements UserRepository {

    private final UserJpaRepository jpaRepository;

    public UserRepositoryImpl(UserJpaRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    @Override
    public User save(User user) {
        UserJpaEntity entity = toEntity(user);
        UserJpaEntity saved = jpaRepository.save(entity);
        return toDomain(saved);
    }

    @Override
    public Optional<User> findByEmail(Email email) {
        return jpaRepository.findByEmail(email.value()).map(this::toDomain);
    }

    @Override
    public boolean existsByEmail(Email email) {
        return jpaRepository.existsByEmail(email.value());
    }

    // ---------- 매핑 ----------

    private UserJpaEntity toEntity(User user) {
        return new UserJpaEntity(
            user.id().value(), user.email().value(), user.passwordHash(),
            user.name(), user.createdAt(), user.updatedAt()
        );
    }

    private User toDomain(UserJpaEntity entity) {
        return User.reconstitute(
            UserId.of(entity.getId()),
            Email.of(entity.getEmail()),
            entity.getPasswordHash(),
            entity.getName(),
            entity.getCreatedAt(),
            entity.getUpdatedAt()
        );
    }
}
```

**포인트**
- `@Repository` — Spring 빈 등록
- **도메인 `UserRepository` 인터페이스 구현**
- JPA 엔티티와 도메인 간 **양방향 매핑** 담당
- `reconstitute`를 써서 DB 데이터 복원 시 중복 검증 생략

## 5. 의존성 방향 (핵심)

```
Domain (UserRepository 인터페이스 정의)
   ▲
   │ 구현
   │
Infrastructure (UserRepositoryImpl)
```

**Infrastructure가 Domain에 의존**하지, **Domain이 Infrastructure에 의존하지 않는다**.
이게 **의존성 역전 원칙(DIP)** 의 실천.

## 6. 도메인 모델 vs JPA 엔티티 분리의 이득

### 분리하지 않으면 (전통적 Spring)
```java
@Entity
public class User {
    @Id @GeneratedValue private Long id;
    @Column private String email;
    // 비즈니스 메서드
    public void changeEmail(String email) { /* ... */ }
}
```

**문제점**
- 도메인 객체에 JPA 강제 (기본 생성자, setter, `@Entity`)
- 불변성 깨짐 (JPA는 setter 선호)
- Lazy loading 프록시로 인한 `==` 동등성 문제
- 테스트 시 DB 필요 (`@DataJpaTest` 등 무거움)
- DB 스키마 변경이 도메인에 직접 영향

### 분리하면 (현재 방식)
- 도메인: 순수 자바, JPA 몰라도 됨
- JPA 엔티티: 기술 세부, DB 친화
- **매핑 코드가 추가되지만**, 두 모델 독립적으로 진화 가능

### 대가
- 매핑 코드 작성 비용
- 객체 생성 오버헤드 (대부분의 경우 무시 가능)

**DDD 프로젝트에서는 분리가 정석**. CRUD 위주면 합쳐 써도 OK.

## 7. SQL 다루는 3가지 레벨

### 레벨 1. 메서드 이름 쿼리 (현재 사용)
```java
Optional<UserJpaEntity> findByEmail(String email);
List<UserJpaEntity> findByNameContainingAndCreatedAtAfter(String name, Instant after);
```
- Spring Data가 이름 파싱 → SQL 자동 생성
- **간단한 조회에 최적**

### 레벨 2. `@Query` (JPQL)
```java
@Query("SELECT u FROM UserJpaEntity u WHERE u.email = :email AND u.createdAt > :since")
Optional<UserJpaEntity> findRecentByEmail(@Param("email") String email, @Param("since") Instant since);
```
- 객체 기준 JPQL 직접 작성
- **조건 조합이 복잡할 때**

### 레벨 3. QueryDSL / Native SQL
```java
// QueryDSL — 타입 안전, 동적 쿼리 가능
queryFactory.selectFrom(user)
    .where(user.email.eq(email).and(user.createdAt.after(since)))
    .fetch();

// Native SQL — DB 고유 기능 필요할 때
@Query(value = "SELECT ... FROM users WHERE ...", nativeQuery = true)
```
- **복잡한 조회, 통계, 리포트**

## 8. 외부 시스템 어댑터 패턴

향후 JWT/이메일/Kafka 등이 추가될 때 패턴:

```java
// Domain 또는 Application이 인터페이스 정의
public interface JwtTokenService {
    String issue(UserId userId);
    UserId verify(String token);
}

// Infrastructure가 실제 구현
@Component
public class JwtTokenProviderImpl implements JwtTokenService {
    // jjwt 라이브러리로 실제 구현
}
```

**규칙**
- 인터페이스는 Domain/Application에 위치 (의존 방향 유지)
- 구현은 Infrastructure에 위치
- 라이브러리 교체(jjwt → nimbus) 시 구현만 바꾸면 끝

## 9. 언제 Infrastructure에 추가하나

**기준: "외부 세계(IO)가 관여하면 Infrastructure"**

| 행위 | 계층 |
|---|---|
| DB 읽기/쓰기 | Infrastructure |
| HTTP 호출 (외부 API) | Infrastructure |
| 파일 읽기/쓰기 | Infrastructure |
| 메시지 큐 발행/수신 | Infrastructure |
| 이메일/SMS 발송 | Infrastructure |
| JWT 서명/검증 | Infrastructure |
| 캐시 읽기/쓰기 | Infrastructure |
| 순수 계산 | **Domain** |
| 시나리오 조율 | **Application** |

## 10. 자주 하는 질문

### Q. 도메인과 JPA 엔티티 나누기 진짜 해야 하나?
**DDD 원칙**: Yes. **실용 관점**: 프로젝트 복잡도에 따라.
- 복잡한 도메인(예약, 결제, 주문) → 분리 강력 추천
- 단순 CRUD (관리 페이지) → 합쳐도 OK

이 프로젝트는 분리 선택 (도메인 복잡도 예상되므로).

### Q. `@Repository` 꼭 붙여야?
Spring Data가 리포지토리 인터페이스는 자동으로 빈 등록.
**구현 클래스**(`UserRepositoryImpl`)에는 **명시적으로** `@Repository` 붙임 (빈 인식 + 예외 변환).

### Q. Transaction은 어디에?
**Application 계층의 UseCase**에만. Infrastructure는 이미 트랜잭션 안에서 실행됨.
`UserRepositoryImpl`에 `@Transactional` 붙이지 않음.

### Q. Domain → Infrastructure 의존이 필요하면?
**절대 금지**. 필요하다고 느껴지면:
- 인터페이스를 Domain에 정의, Infrastructure가 구현
- Spring의 DI로 런타임에 주입

이게 **의존성 역전(DIP)** 의 핵심.

### Q. JPA N+1 문제는 어디서 해결?
Infrastructure에서. `@EntityGraph`, fetch join, `@BatchSize` 등.
**도메인은 N+1을 모른다** — Infrastructure가 숨긴다.

## 11. 한 줄 요약

> **Infrastructure = "도메인이 외부 세계와 소통하는 창구 구현체"**.
> Domain이 "무엇이 필요한지" 선언하면, Infrastructure가 JPA/Redis/SMTP 등으로 **"어떻게 할지"** 구현한다.
