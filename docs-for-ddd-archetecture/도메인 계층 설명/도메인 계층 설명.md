# Domain 계층 설명

## 1. 한 줄 정의

> **"비즈니스 개념과 규칙 그 자체"가 사는 곳.**
> 다른 어떤 계층에도 의존하지 않는 **가장 안쪽의 핵심**.

## 2. 여기에 들어가는 것

| 종류 | 예시 (auth) | 설명 |
|---|---|---|
| **Value Object** | `Email`, `UserId` | 값 자체가 정체성. 불변. 항상 유효한 상태. |
| **Aggregate Root** | `User` | 관련 객체들의 묶음을 대표하는 진입점 |
| **Domain Exception** | `DuplicateEmailException`, `InvalidEmailException`, `WeakPasswordException` | 비즈니스 규칙 위반 |
| **Repository 인터페이스** | `UserRepository` | 저장소 계약 (구현은 Infra) |
| *(나중에)* Domain Service | `PasswordHasher` 인터페이스 등 | 여러 Aggregate 걸친 로직 |
| *(나중에)* Domain Event | `UserRegistered` | 도메인에서 발생한 사건 |

## 3. 실제 패키지 구조

```
auth/domain/
├── model/
│   ├── UserId.java          ← Value Object (UUID 기반 식별자)
│   ├── Email.java           ← Value Object (형식 검증 내장)
│   └── User.java            ← Aggregate Root
├── exception/
│   ├── InvalidEmailException.java
│   ├── DuplicateEmailException.java
│   └── WeakPasswordException.java
└── repository/
    └── UserRepository.java  ← 인터페이스만
```

## 4. 핵심 코드 발췌

### Email — Always-Valid Value Object

```java
public final class Email {
    private static final Pattern EMAIL_PATTERN = Pattern.compile(
        "^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$"
    );
    private static final int MAX_LENGTH = 254;

    private final String value;

    private Email(String value) { this.value = value; }

    public static Email of(String raw) {
        if (raw == null || raw.isBlank())
            throw new InvalidEmailException("Email must not be blank");
        String normalized = raw.trim().toLowerCase();
        if (normalized.length() > MAX_LENGTH)
            throw new InvalidEmailException("Email exceeds max length: " + MAX_LENGTH);
        if (!EMAIL_PATTERN.matcher(normalized).matches())
            throw new InvalidEmailException("Invalid email format: " + raw);
        return new Email(normalized);
    }

    public String value() { return value; }
    // equals/hashCode는 value 기준
}
```

**포인트**
- 생성자 `private` — 외부에서 `new Email(...)` 불가
- `Email.of()` 정적 팩토리만이 유일한 생성 경로
- **이 타입을 가진 변수는 반드시 유효** (Always-Valid)

### UserId — 도메인이 직접 생성하는 식별자

```java
public final class UserId {
    private final UUID value;

    private UserId(UUID value) {
        this.value = Objects.requireNonNull(value);
    }

    public static UserId generate() {
        return new UserId(UUID.randomUUID());   // DB 없이 도메인이 생성
    }

    public static UserId of(UUID value) { return new UserId(value); }
    public static UserId of(String value) { return new UserId(UUID.fromString(value)); }
}
```

**왜 DB auto-increment 대신 UUID를 도메인에서 생성?**
- 객체 생성 시점에 ID가 이미 확정 → "저장 전/후" 반쪽 상태 없음
- `save()`가 부수효과 없는 순수 저장 함수가 됨
- 분산/마이크로서비스 환경 대응 (ID 충돌 없음)
- URL에서 순차 추측 불가 (보안)
- 테스트 시 DB 없이 도메인 테스트 가능

### User — Aggregate Root

```java
public class User {
    private final UserId id;
    private final Email email;
    private final String passwordHash;   // 이미 해시된 값
    private final String name;
    private final Instant createdAt;
    private final Instant updatedAt;

    public static User register(UserId id, Email email, String passwordHash,
                                String name, Instant now) {
        if (passwordHash == null || passwordHash.isBlank())
            throw new IllegalArgumentException("passwordHash must not be blank");
        if (name == null || name.isBlank())
            throw new IllegalArgumentException("name must not be blank");
        return new User(id, email, passwordHash, name.trim(), now, now);
    }

    // Infrastructure에서 DB 데이터를 도메인으로 복원할 때 사용
    public static User reconstitute(UserId id, Email email, String passwordHash,
                                    String name, Instant createdAt, Instant updatedAt) {
        return new User(id, email, passwordHash, name, createdAt, updatedAt);
    }
}
```

**포인트**
- `register()` — 신규 가입 시 팩토리 (불변식 검증 수행)
- `reconstitute()` — DB에서 복원 시 전용 (검증 재실행 생략)
- **JPA 어노테이션 없음** — 도메인은 DB를 모름
- `passwordHash`만 받음 — 도메인은 BCrypt 같은 해시 알고리즘을 몰라야 함

### UserRepository — 도메인이 정의하는 계약

```java
public interface UserRepository {
    User save(User user);
    Optional<User> findById(UserId id);
    Optional<User> findByEmail(Email email);
    boolean existsByEmail(Email email);
}
```

**포인트**
- **인터페이스만** 도메인에 있음
- 구현체는 `infrastructure/persistence/UserRepositoryImpl`에 위치
- 도메인이 "무엇이 필요한지" 선언하고, 인프라가 "어떻게 할지" 구현 (DIP)

## 5. 도메인 순수성 규칙

이 계층의 파일에 다음이 있으면 **위반**:

```java
❌ import jakarta.persistence.*   // JPA (@Entity, @Column 등)
❌ import org.springframework.*   // Spring (@Service, @Component 등)
❌ import jakarta.validation.*    // Bean Validation (@NotBlank, @Email 등)
❌ import org.hibernate.*         // Hibernate
❌ import lombok.*                // 의견 갈림 (팀마다 허용/금지)
```

**허용되는 import**
- `java.*` (자바 표준)
- 같은 도메인 패키지 내부
- 순수 도메인 라이브러리 (예: vavr, 선택적)

## 6. 왜 이렇게 엄격한가

### 이유 1. 기술 교체에 독립
- JPA → MyBatis로 바꿔도 도메인은 그대로
- PostgreSQL → MongoDB로 바꿔도 도메인은 그대로
- Spring → Quarkus로 바꿔도 도메인은 그대로

### 이유 2. 테스트 속도/안정성
```java
@Test
void 이메일_대문자는_소문자로_정규화된다() {
    Email email = Email.of("USER@Example.COM");
    assertThat(email.value()).isEqualTo("user@example.com");
}
```
Spring 컨텍스트 X, DB X, 순수 자바 테스트. 수백 개가 수초.

### 이유 3. 비즈니스 규칙이 읽기 쉬움
Email의 규칙을 알고 싶다? → `Email.java` 한 파일만 열면 끝.
JPA/Spring 어노테이션과 섞여 있지 않아 **규칙만 선명하게** 보임.

## 7. 의존성 방향

```
Presentation → Application → Domain ← Infrastructure
                              ▲
                              │
                           (의존 없음)
```

**Domain은 그 누구에게도 의존하지 않는다.** 반대로 **모든 계층이 Domain에 의존한다.**

## 8. 자주 하는 질문

### Q. `String` 대신 꼭 `Email` VO로 감싸야 하나?
**원칙적으론 Yes.** 실무에선 **핵심 개념만** VO로 만듦:
- 검증 규칙이 있는 것 (Email, Password)
- 의미가 중요한 것 (Money, Quantity)
- 도메인 용어로 이름 붙일 가치 있는 것 (UserId, OrderId)

단순 `name` 같은 건 `String`으로 두는 경우도 많음. 균형 감각 필요.

### Q. Aggregate Root는 어떻게 정하나?
**"트랜잭션 일관성이 필요한 단위"**.
- `User`는 그 자체로 하나
- `Order`는 `OrderItem`들을 포함 (Order가 Root, OrderItem은 그 내부)
- 외부 코드는 `Order`를 통해서만 `OrderItem`에 접근 가능

### Q. 도메인 예외는 `RuntimeException`으로 해야 하나?
거의 **Yes**. Checked Exception은 호출자 코드를 지저분하게 만들고, 자바 외 언어에도 없는 개념이라 요즘은 Unchecked(Runtime)가 표준.

### Q. 왜 `Email.of()`가 `Email.parse()` 아니고 `of`인가?
자바 관례:
- `of(...)` — 값들로부터 인스턴스 생성 (`List.of`, `Optional.of`)
- `from(...)` — 다른 타입에서 변환 (`LocalDate.from`)
- `valueOf(...)` — 원시타입↔래퍼 (구세대)

VO에는 `of`가 관례적.

## 9. 한 줄 요약

> **Domain = "이 시스템의 비즈니스가 무엇인가"의 순수한 표현.**
> JPA/Spring 없이도 단독으로 컴파일되고 테스트되는, 시스템의 심장.
