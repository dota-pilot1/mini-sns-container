## 참고 — 이번 세션에서 내린 주요 결정

- **DDD 패턴 고수**: user 모듈과 동일 구조로 미러링, Spring/JPA 가 domain/에 새지 않도록 유지
- **soft delete** (deletedAt Instant) — hard delete 대신
- **시드는 API 경유** (`CreateRoomUseCase.execute`) — 검증 로직 그대로 태움
- **클라이언트 필터링** (60개 규모) — 서버 왕복 없이 카운트 정확
- **낙관적 업데이트 + 순차 bulk** — 병렬 bulk 는 snapshot race 우려
- **TanStack Table 계속 사용** — AG Grid 전환 비용 > 이득 (인라인 편집 필요 시 특정 컬럼만 붙임)
- **URL 은 single source of truth** — `useState` 대신 `useSearch` + `navigate({ search, replace })`
- **"+ 방 등록" 모달은 로컬 state** — 일회성 입력, URL 공유 가치 낮음 (일관된 예외)

## 2차 세션 주요 결정

- **교과서 DDD — 상태 전이는 컬럼, 테이블 이동 아님**: 입주/퇴실이 레코드를 다른 테이블로 옮기는 게 아니라 `tenants.status` 만 UPDATE → 이력 보존, FK 안전
- **User vs Tenant 분리**: 인증(`users`, 관리자 로그인) 과 CRM(`tenants`, 입주자) 은 다른 개념이라 애그리거트/테이블 분리
- **roomId 는 tenants 에 둠** (FK 없이 UUID 참조): Room/Tenant 애그리거트 경계 존중, 참조 무결성은 애플리케이션 레벨
- **`clearRoom` boolean 플래그**: PATCH 에서 "null = 변경 없음" vs "null = 해제" 모호성 해결
- **ddl-auto=update 한계**: 컬럼 drop 불가 → 수동 ALTER 로 해결 (prod 에서는 Flyway 도입 필요)
