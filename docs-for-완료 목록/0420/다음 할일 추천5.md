## 완료 — 입주 관리 풀세트

### 계약 도메인
- Contract aggregate + `previousContractId` 체인 (재계약/연장은 새 레코드 append)
- 불변 Contract (종료일은 `truncateEndDate` 로만 단축 가능)
- Soft delete + 체인 보존
- 커밋: [3c7d27c](https://github.com/dota-pilot1/stay-ops-container/commit/3c7d27c)

### 상태 머신 (`cancelledAt` 기반)
- 파생 상태 4개: `UPCOMING · EFFECTIVE · OVERDUE · CANCELLED`
- 저장은 `cancelledAt: LocalDate?` 한 컬럼만 — 나머지는 날짜 + 이 컬럼으로 파생
- "자연 만료" 개념 제거 (관리자가 명시적 퇴실 처리 안 하면 끝나지 않음)
- 중도 취소 / 정상 퇴실 구분 X — 둘 다 관리자 액션이라 의미 없음

### 운영 플로우
- `CancelOccupancyUseCase` 로 퇴실 처리 통합:
  - EFFECTIVE → `endDate` 단축 + `cancelledAt` + PAID 환불
  - OVERDUE → `endDate` 유지 + `cancelledAt` + 보증금 환불 기본 ON
- `CancelOccupancyDialog` 컨텍스트 스위치: "계약 취소" ↔ "퇴실 처리"
- 좌측 체인 목록 / 우측 환불 예상 레이아웃 (CANCELLED 는 비활성)

### 입주자 관리 페이지
- 4컬럼: 회원 / 거주중 / 연체 / 퇴실
- 거주중 카드에 `D-N` 만료 카운트다운 (≤7일 rose, ≤30일 amber)
- UPCOMING 은 거주중 컬럼에서 "예정 D-N" 배지
- 컬럼 헤더에 `전체 / D-7 / D-10 / D-30` 필터 토글
- 연체 카드: "만료 +N일" + 퇴실 처리 버튼

### 방 상세 드로어
- `계약 목록 N / + 추가 / 취소 (or 퇴실 처리)` 액션 3종 통합
- 거주중 배지 중복 제거, `4월 완납` 처럼 결제 뱃지에 기간 명시
- OVERDUE 도 "현재 방 사용자" 로 노출, 버튼 상황별 변신

## 남은 3가지

### 1. 대시보드 📊

**할 일**
- `/` 루트를 관리자 홈으로 재설계
- 위젯
  - **수금 현황**: 이번 달 N명 중 M명 완납 (진행 바) + 미납 TOP 5
  - **계약 만료 임박**: 7일 / 30일 이내 TOP 5 (입주자 페이지 필터 재활용)
  - **공실 현황**: 상태별 방 수 (공실·예약·입실·청소·문제) + 도넛
  - **오늘의 이슈**: 🔴 문제 방 / 연체 퇴실 대기 목록
  - **월 매출 요약**: 이번달 PAID 합계 vs 계약 이론 매출

**왜 1순위**
- **데이터가 이미 다 있음** — 신규 API 0개, `/api/rooms` + `/api/contracts` + `/api/payments` 조합
- 가장 빠른 가시적 성과 + "이제 시스템이 뭘 해주는지" 한 화면에서 설명 가능
- 2번(실결제) 작업 시 실시간 효과를 여기서 눈으로 확인 가능

**범위**: 2~3 커밋.

---

### 2. 권한 관리 + 입주자 포털 🔐

**할 일**
- `Role` enum: `OWNER / MANAGER / TENANT`
- JWT claims 에 role 포함, `@PreAuthorize` 로 엔드포인트 제한
- 프론트: 역할별 메뉴 / 라우트 가드 / nav 분기
- **입주자 포털 (MVP 조회 전용)**:
  - 내 계약 + 체인 이력
  - 내 방 (이미지 포함)
  - 내 납부 내역 + 이번 달 미납 알림
  - (3번 완료되면 결제 링크로 바로 납부)

**왜 2순위**
- **기반 인프라 성격** — 모든 엔드포인트에 퍼지는 횡단 관심사. 나중에 붙이면 회귀 리스크 크고, 먼저 잡아두면 이후 작업(실결제 포함) 모두 그 위에서 안전하게 진행
- **외부 의존성 없음** — 순수 내부 코드라 PG 심사 기다릴 필요 없이 바로 시작 가능
- 포털 데이터 이미 충분 — 수동 Payment 기록이 쌓여 있어서 "내 납부 내역" 표시에 실결제 연동 불필요
- Role 분리만 먼저 있어도 건물주 ↔ 총무 권한 위임 즉시 가능

**범위**: 서버 2~3 커밋 + 프론트 3~4 커밋.

### 3. 실결제 연동 💳

**현재 상태**
- `Payment` 애그리거트 + 수동 입력 / PAID·REFUNDED 상태 / 환불 전액 처리 완료
- `source` 필드 열어둠 → webhook 붙일 준비 OK

**할 일**
- 결제 PG 결정 (토스 / 카카오 / NICE) — 심사 기간 오래 걸리니 **이 단계 시작 시점에 먼저 신청 걸어두기**
- `POST /webhooks/payments/:source` 핸들러
  - 서명 검증, 중복 방지(idempotency key), Payment 레코드 생성
- 관리자 UI:
  - "결제 링크 생성" → 입주자에게 공유 → 자동 PAID 기록
  - 수동 입력은 남겨둠 (현금 입금 대응)
- 입주자 포털에서 결제 링크로 바로 납부 (2번과 연동)

**왜 마지막**
- PG 심사 대기 시간(2~4주)을 1·2 개발에 활용 가능 — 심사 통과 시점에 딱 2번 끝나고 3번 들어가기 좋음
- 자동화는 수동 입력이 되고 있는 시점에서 덧붙이는 "위에 쌓는" 작업이라 뒤로 미뤄도 손해 적음
- Role 이 먼저 있어야 webhook 엔드포인트 권한(서버-서버 간 공개, 관리자 전용 등) 깔끔하게 분리

**범위**: 서버 2~3 커밋 + 프론트 1~2 커밋. PG 심사 기간 별도.

## 설계 원칙 (유지)

- **상태는 파생**: Contract `cancelledAt` 처럼 최소 저장 + 날짜 기반 계산
- **수동 먼저, 자동화 나중**: Payment `source` 필드로 webhook 확장 경로 이미 마련
- **포털은 내용물이 채워진 뒤에**: 빈 껍데기 방지
- **기반 인프라 먼저, 자동화 나중**: Role 처럼 횡단 관심사는 먼저 깔고 위에 쌓기
