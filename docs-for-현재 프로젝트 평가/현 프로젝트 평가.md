# 현 프로젝트 평가

2026-04-20 기준. 정직한 내부 평가 — 과장은 빼고 강점·약점을 있는 그대로 적어둔다.

---

## TL;DR

- **관리 프로토타입 성격**: 부분적으로 맞음. "주체 → 자원 → 계약 → 결제" 공통 뼈대는 재사용 가능.
- **DDD 아키텍처**: 레이어링은 정석. "엔터프라이즈" 자칭은 과장. 정확한 표현은 **"잘 짜인 중규모 DDD 프로젝트"**.
- **DB 설계**: 단단한 편. 프로덕션 전 Flyway · FK · audit · 낙관적 락 추가 필요.

---

## 1. 관리 프로토타입 성격

프로젝트 뼈대가 `주체(User/Tenant) · 자원(Room) · 사용 계약(Contract) · 결제(Payment)` 라 **자원 예약/할당/정산 패턴** 쪽은 그대로 재사용 가능.

### 잘 맞는 도메인

| 도메인 | 매핑 | 재사용성 |
|---|---|---|
| 미용실 예약 | Room=좌석, Contract=예약 세션, chain=재방문 | ★★★★ |
| 동호회 관리 | Tenant=회원, Contract=이벤트 참여, Payment=회비 | ★★★★ |
| 시설 예약 (체육관 등) | Room=시설, Contract=예약 슬롯 | ★★★★ |
| 멤버십 서비스 | Contract chain = 구독 갱신 이력 | ★★★ |

### 결이 다른 도메인

- **콜센터**: 티켓=Contract 로 볼 수 있으나 SLA, 큐잉, 상담원 배정 등 특수 로직이 본질. 뼈대만 공유.
- **스마트 팩토리**: 시계열 센서 데이터 / OEE 계산 / MES 가 핵심. 이 프로젝트와 거의 다른 도메인.
- **전자상거래**: 상품-주문 모델이 달라서 Contract 개념이 안 맞음.

### 결론

**"사람-자원-세션-결제"** 구조의 서비스 예약·멤버십·시설 관리류에 한해 공통 프로토타입. "어지간한 관리 프로젝트 다 커버" 는 과장.

## 2. DDD 아키텍처 평가

### 잘 지킨 것 ✅

- **헥사고날 레이어링**: `domain / application / infrastructure / presentation` 깔끔하게 분리
- **Aggregate 불변성**: `final` 필드 + 팩토리 메서드 + 복사 연산 (Contract, Room 등)
- **Value object**: `ContractId`, `RoomId` 등 원시 UUID 를 감쌈
- **도메인 예외 분리**: `InvalidContractFieldException`, `ContractNotFoundException` 등 예외를 도메인 계층에 둠
- **파생 상태 계산**: Contract 의 UPCOMING/EFFECTIVE/OVERDUE/CANCELLED 를 컬럼이 아닌 `cancelledAt` + 날짜 조합으로 계산 (저장 중복 제거)
- **Use case 단위 분리**: `CreateContractUseCase`, `CancelOccupancyUseCase`, `ExtendAndPayUseCase` 각각 단일 책임

### 빠진 "엔터프라이즈급" 요소 ❌

- **도메인 이벤트 발행 / 이벤트 소싱** 없음 — Contract 취소 시 Payment 환불이 같은 Use case 안에서 직접 호출되는 강결합
- **CQRS** (읽기·쓰기 모델 분리) 없음 — read-heavy 대시보드 확장 시 병목 우려
- **분산 트랜잭션 / Saga** 없음 — 단일 DB 트랜잭션에 의존
- **Audit trail** 없음 — 누가 언제 뭘 바꿨는지 추적 불가
- **Observability** (metrics, tracing, structured logging) 없음
- **멀티 테넌시 / 샤딩** 없음 — 건물 여러 개 운영 대비 X
- **메시지 브로커 (Kafka 등)** 없음 — 비동기 처리 / 외부 시스템 연동 기반 없음

### 정확한 포지셔닝

**"잘 짜인 중규모 DDD 프로젝트"**. 학습·포트폴리오·스타트업 MVP 로는 탁월. "엔터프라이즈" 는 과한 표현.

## 3. DB 설계 평가

### 잘한 것 ✅

- **UUID PK** — 분산 환경·보안 대비
- **Soft delete** (`deletedAt`) — 데이터 유실 방지 + 복구 가능
- **적절한 인덱스** — `tenant_id`, `room_id`, `end_date`, `cancelled_at` 등
- **금액은 원 단위 `long`** — 부동소수점 오차 회피
- **계약 불변 + chain** — 이력 보존, 재계약·갱신을 append-only 로 처리
- **Nullable semantic 컬럼** — `cancelledAt`, `previousContractId` 가 의미를 담음
- **상태는 저장 대신 파생** — 배치 동기화 불필요

### 프로덕션 전 보완 필요 ❌

| 항목 | 현황 | 필요한 것 |
|---|---|---|
| 마이그레이션 | `ddl-auto=update` | **Flyway / Liquibase** (스키마 버전 관리 필수) |
| 외래키 | JPA 엔티티에 UUID 만 보유 | **DB 레벨 FK 제약** (일관성 보장) |
| Audit 컬럼 | 없음 | `created_by`, `updated_by` |
| 낙관적 락 | 없음 | `@Version` (동시 수정 유실 방지) |
| 대용량 대응 | 없음 | 결제·계약 테이블 **파티셔닝·아카이빙** 전략 |

## 4. 강점 총정리

1. **깨끗한 레이어링** — 도메인 로직이 프레임워크 · 영속화 · 프레젠테이션에서 분리
2. **불변 Aggregate** — Contract, Room 등 도메인 규칙이 생성자/팩토리에 집중
3. **상태 파생 모델** — 이중 진실(dual source of truth) 없이 날짜 + 최소 컬럼으로 상태 표현
4. **append-only 이력** — 계약 체인 · soft delete 로 과거 보존
5. **적절한 인덱스 / UUID / 원 단위 금액** 등 DB 기초 탄탄
6. **프론트·백 도메인 언어 일치** — UPCOMING/EFFECTIVE/OVERDUE/CANCELLED 4상태를 양쪽에서 동일하게 파생

## 5. 개선 우선순위

### 프로덕션 띄우기 전 필수

1. **Flyway** — 스키마 마이그레이션 도구 도입
2. **DB 레벨 FK 제약** — 앱 버그로 인한 고아 레코드 방지
3. **낙관적 락** — 동시 수정 유실 방지
4. **Audit 컬럼** — 누가 언제 뭘 바꿨는지
5. **Observability** — 최소한 Micrometer + OpenTelemetry 기반 tracing

### 성장기에 추가

1. **도메인 이벤트** — Use case 간 강결합 해소 (Contract 취소 → Payment 환불을 이벤트로)
2. **CQRS** — 대시보드·보고서용 읽기 모델 분리
3. **멀티 테넌시** — 건물 여러 채 운영 대비 `building_id` 파티션 키
4. **결제 아카이빙** — 오래된 Payment 를 별도 테이블로 이관

## 6. 결론

**학습·포트폴리오·스타트업 MVP 관점에서는 탁월**. 다음 두 가지는 구분해서 인식:

- "공통 관리 프로토타입" — 부분적으로 맞음. 자원 예약·멤버십 계열엔 거의 그대로 이식 가능. 팩토리·콜센터·이커머스 등 특수 도메인엔 뼈대만 공유.
- "엔터프라이즈 DDD" — 레이어링은 정석이지만 엔터프라이즈 규모 대응 (이벤트·CQRS·멀티테넌시·observability) 은 아직. **"잘 짜인 중규모 DDD 프로젝트"** 가 정확한 이름.

프로덕션 전 체크리스트: **Flyway + FK + Audit + 낙관적 락 + Observability**. 이 다섯이 갖춰지면 실서비스 1~10만 사용자 규모까진 자신 있게 올릴 수 있는 뼈대.

## 7. 참고 프로젝트 / 아키텍처 템플릿으로서의 가치

앞 장들의 비판은 "엔터프라이즈 규모 대응" 관점이었고, **참고/템플릿 프로젝트** 관점에서는 분명히 상위권. 실제로 가치 있는 지점들:

### 교보재로서 잘 보여주는 것

- **헥사고날 레이어링을 과하게 추상화하지 않고 실제로 돌아가는 코드로 구현** — 학습자가 이론서보다 여기서 배우기 쉬움
- **DDD 핵심 패턴이 살아있는 예제**로 들어감:
  - Aggregate 불변 (final 필드 + 팩토리 + 복사 연산)
  - Value object (`ContractId`)
  - 파생 상태 (cancelledAt + 날짜 조합)
  - Append-only 체인 (재계약 이력)
  - Soft delete
- **프론트-백 도메인 언어 일치** — UPCOMING/EFFECTIVE/OVERDUE/CANCELLED 4상태를 양쪽에서 동일 파생. 풀스택 DDD 샘플로 드묾
- **설계 고민 흔적이 커밋 히스토리에 남음** — ContractStatus 컬럼 제거 → 날짜 파생 전환 같은 의사결정 과정이 보여서 "왜 이렇게 했는가" 를 추적 가능

### 적당히 뺀 것도 장점

- **이벤트 소싱 / CQRS / Saga 없음** → 오버엔지니어링 함정 피함. 중규모 서비스엔 이게 정답
- **불필요한 인터페이스 남발 없이** 실제로 쓰이는 추상화만
- **프레임워크 의존은 infrastructure 에만** — domain 은 Spring-free 로 순수 자바. 테스트성 높음
- **Contract 상태 enum 을 다시 안 넣는 결정** — "상태는 파생, 저장은 최소" 원칙을 끝까지 지킴

### 새 프로젝트 시작할 때 얻는 것

- **도메인만 바꿔 끼우면 되는 뼈대** — Contract → 예약/주문/티켓/세션 등으로 변주 용이
- **"이 정도 규모에선 이 정도 복잡도가 적정"** 이라는 감각의 기준점
- **프로덕션 전 보완 목록까지 투명하게 드러남** — 뭘 더 해야 하는지 아는 상태로 출발
- **프론트엔드 레퍼런스도 얻음** — TanStack Router + React Query + Tailwind v4 + zod 조합이 실제 동작하는 모범 사례

### 포지셔닝

포트폴리오 / 교육용 / 스타트업 스타터킷 관점에서는 **상위 10% 수준**. 특히 아래 셋이 동시에 잡힌 경우는 흔치 않음:

1. DDD 레이어링이 교과서적
2. 도메인 언어가 프론트까지 일관
3. 과엔지니어링 없이 중규모 MVP 에 맞는 복잡도

"엔터프라이즈 수준" 이라고 자칭하지 않고 **"잘 정제된 참조 구현"** 으로 포지셔닝하면, 실제로 누구한테 보여줘도 설계력 검증된 프로젝트로 받아들여짐.
